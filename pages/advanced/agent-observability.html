Agent Observability

Agent observability is the control room for AI-assisted work. It captures what the agent was asked to do, what context it used, which tools it called, what changed, what validation ran, where approvals happened, and why a human should trust or reject the result.

Execution traces Tool-call evidence Audit-ready review

Observability is how you turn “the agent did stuff” into evidence.

Traditional software observability looks at logs, metrics, and traces. Agent observability keeps those ideas, then adds agent-specific evidence: prompts, retrieved context, tool choices, tool arguments, file diffs, command output, approvals, blocked actions, and final validation.

The goal is not to record everything forever. The goal is to reconstruct enough of the run to answer: what happened, why was it allowed, what changed, what proved it, and who owns the result?

Monitoring, observability, and audit are cousins, not clones.

Monitoring tells you whether something looks wrong. Observability lets you investigate how the run unfolded. Audit lets you prove what happened later. Agent work needs all three because tool-using AI can move from text to action faster than a reviewer can say, “wait, what branch was that?”

  • Monitoring watches health and thresholds.
  • Observability reconstructs the path.
  • Audit preserves accountability.

The four signal families.

Do not rely on a single chat transcript. Agent work leaves different kinds of evidence, and each one answers a different question.

T

Traces

The ordered path of the run: request, planning step, retrieval, tool calls, file edits, commands, validation, approvals, and final response.

L

Logs

Structured events that explain what occurred at each step, including warnings, errors, blocked actions, retries, and policy decisions.

M

Metrics

Counts and rates: tool-call volume, error rate, retry count, latency, token use, cost, approval rate, blocked action rate, and validation pass rate.

A

Artifacts

The durable outputs: diffs, generated files, screenshots, test reports, plans, tickets, pull requests, deployment records, and rollback notes.

The execution trace should read like a flight recorder.

A good trace is not a pile of vibes wearing timestamps. It should let a reviewer walk the run from request to result without needing to trust the agent’s memory.

Request

User, task, risk level, requested output, explicit constraints, and stop condition.

Context

Files, snippets, search results, retrieval hits, instruction files, and sources the agent actually used.

Plan

Selected approach, assumptions, scope boundaries, non-goals, and known uncertainty.

Tools

Tool names, arguments, targets, permissions, outputs, errors, and blocked calls.

Changes

Files created, files modified, diffs, generated artifacts, and areas intentionally left untouched.

Validation

Commands run, tests passed or failed, screenshots, lint results, review checks, and remaining gaps.

Handoff

Final result, owner, approvals, next actions, rollback notes, and evidence links.

What to capture, and what to avoid capturing.

More logging is not automatically better. Capture enough to reconstruct the work, but do not turn observability into a secret blender.

Capture the evidence, not the radioactive glitter.

Task identityRequest ID, user, workspace, repository, branch, ticket, environment, and agent identity.
Context referencesFile paths, source IDs, retrieval query, result count, document version, and hashes where practical.
Model and settingsModel, tool set, permission rung, system profile, temperature-like settings, and relevant policy mode.
Tool callsTool name, arguments, target, result summary, error, retry count, and whether the call was allowed or blocked.
Change evidenceDiffs, generated files, screenshots, command output, validation reports, and affected paths.
Approval chainWho approved what, at which step, with which exact arguments, and what remained blocked.
Do not capture secretsRedact tokens, credentials, private keys, cookie values, sensitive customer data, and tool outputs that should not persist.
Do not rely on hidden reasoningRecord decisions, summaries, evidence, and outcomes. Do not require private chain-of-thought as the audit record.
Do not preserve stale noiseOld context, duplicate logs, full private documents, and irrelevant tool payloads make review harder, not safer.

Observability matrix by permission level.

The higher the agent can climb on the permissions ladder, the stronger the evidence trail should become.

Read and explain Sources used, sources not inspected, uncertainty, and output summary. Did the answer depend on the right material? Low

Dashboards should answer operational questions.

A dashboard that only shows “number of agent runs” is a decorative speedometer on a parked canoe. Useful dashboards connect activity to quality, risk, and review outcomes.

Q

Quality and validation

  • What percentage of runs produced passing validation evidence?
  • Which tests, checks, or reviews fail most often?
  • How often do humans request rework after agent changes?
  • Which workflows produce the most reliable first-pass results?
R

Risk and permission use

  • Which runs used write tools, external APIs, or elevated permissions?
  • How often did the agent attempt a blocked action?
  • Which repositories, systems, or users trigger the most policy warnings?
  • Where are approvals happening too late or too vaguely?
C

Cost and performance

  • Which tasks burn the most tokens or tool calls?
  • Where do retries, long context, or repeated retrievals inflate cost?
  • Which tools are slow, flaky, or noisy?
  • Where would better summaries or context routing reduce waste?
S

Security and audit

  • Did any run touch sensitive paths, secrets, customer data, or privileged systems?
  • Were sensitive fields redacted before persistence?
  • Can a reviewer reconstruct source-to-tool-to-output flow?
  • Is there enough evidence for incident response?

A small event schema is better than a thousand mystery logs.

Structured events make traces searchable, filterable, and reviewable. Even a lightweight schema can keep agent runs from becoming archaeological digs.

Observable artifacts make review faster.

The final answer should point to evidence, not simply announce success with a little trumpet.

Δ

Diff package

Changed files, new files, deleted files, generated artifacts, and a summary of what each change is meant to accomplish.

✓

Validation package

Commands run, tests passed, checks failed, screenshots captured, and known validation gaps that still need human attention.

↩

Recovery package

Rollback plan, files to revert, backups, feature flags, deployment notes, and what to monitor after the change.

!

Blocked-action package

Actions the agent refused or could not perform, including missing permission, unclear scope, unsafe target, or policy conflict.

#

Trace package

Run ID, source references, tool calls, approvals, and enough timeline detail to replay the decision path.

@

Ownership package

Reviewer, approver, next owner, open questions, and the explicit point where AI assistance ends and human accountability begins.

Reusable agent observability prompt

Use this before, during, or after an agent run when you need the result to be reviewable instead of merely plausible.

For this agent task, produce an observability report. Include: 1. Run objective and requested output. 2. Files, sources, and context used. 3. Permission level or autonomy boundary. 4. Tools called, arguments summarized, and results. 5. Files created, modified, or intentionally not touched. 6. Validation commands, checks, screenshots, or evidence. 7. Errors, retries, blocked actions, and remaining uncertainty. 8. Approval points required before merge, publish, deploy, send, or delete. 9. Rollback or recovery notes. 10. Final owner and next action. Do not include secrets, private credentials, raw sensitive data, or hidden reasoning. Record decisions, evidence, and outcomes instead.

Field guide takeaway: Agent observability is the difference between “the AI changed something” and “we can prove what happened.” A useful agent run should leave a trace of the request, context, tools, permissions, changes, validation evidence, approvals, blocked actions, and ownership so humans can review the work, investigate failures, and decide whether the result is safe to accept.
