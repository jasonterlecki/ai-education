Agent Permissions Ladder

AI agents should not jump from “read this file” to “rewrite the application and deploy it before lunch.” A permissions ladder gives teams a clear way to match autonomy to risk, so agents can be useful without becoming tiny forklifts in a glassware warehouse.

The mistake is treating permission as one big switch.

An agent does not need full access just because it can be helpful. The useful question is not “can the agent do this?” It is “what authority, workspace, evidence, and human checkpoint should exist before this action is allowed?”

01

Capability is not authority

A model may be able to produce code, shell commands, API calls, migration scripts, and deployment plans. That does not mean it should be allowed to execute them. Capability describes what the system can attempt. Authority describes what the team has deliberately permitted.

A safe agent workflow separates thinking, editing, executing, approving, and deploying into visible steps.
02

Risk rises when text becomes action

The early rungs are mostly advisory. The higher rungs can change files, run commands, call APIs, move data, notify people, merge code, or touch production. Each step upward should add stronger scoping, logging, validation, and approval requirements.

  • Read access needs source control.
  • Write access needs boundaries.
  • Execution access needs evidence.
  • Deployment access needs ownership.

The ladder: from observation to operational impact.

Use the ladder as a policy pattern, not a universal law. A content page, a Terraform module, and a production incident may all use the same rungs, but the approval gates should be stricter when the blast radius is larger.

Observe and explain

Allowed: Read supplied context, explain files, summarize logs, compare documents, identify likely issues, and ask for missing inputs.

Typical use

Learning a codebase, reviewing architecture, understanding a bug report, or preparing a meeting summary without making changes.

Gate

Source boundaries. The agent should say what it used, what it did not inspect, and where uncertainty remains.

Recommend and plan

Allowed: Propose options, tradeoffs, risks, implementation phases, validation plans, and rollback considerations.

Typical use

Turning a vague idea into a Vibe Brief, implementation plan, risk review, or acceptance criteria before any work starts.

Gate

Human selection. The agent may recommend, but a person chooses the path, scope, non-goals, and stop conditions.

Draft changes for review

Allowed: Produce proposed patches, page drafts, config examples, scripts, tests, or migration notes without applying them automatically.

Typical use

Generating a reviewed HTML page, a candidate README update, a test file, or a patch preview that a human can inspect first.

Gate

Diff visibility. The agent must show what would change, why it matters, and what validation would prove it works.

Edit inside a fenced workspace

Allowed: Modify files in an approved branch, folder, sandbox, or generated artifact area. No external writes, secrets, production systems, or broad rewrites.

Typical use

Updating a documentation page, creating a new standalone guide, editing tests, or applying a narrow bug fix in a controlled branch.

Gate

Scope fence. The agent needs explicit allowed paths, forbidden paths, naming rules, and “do not touch” areas.

Run local validation commands

Allowed: Execute approved read-only or local commands such as tests, linters, format checks, static analysis, local build previews, or non-destructive diagnostics.

Typical use

Running a test suite, checking HTML validity, generating a preview screenshot, or confirming that a documentation build still works.

Gate

Command allowlist. Commands should be bounded, logged, and non-destructive unless separately approved.

Use external tools with limited write scope

Allowed: Call approved APIs, create drafts, open tickets, label issues, update sandbox data, or interact with MCP tools whose permissions are intentionally narrow.

Typical use

Creating a pull request draft, posting a non-sensitive status summary, updating a staging-only CMS record, or filing a ticket with evidence attached.

Gate

Tool contract. The tool should expose only the action needed, not an all-access backstage pass.

Change shared systems

Allowed: Make changes that affect collaborators, shared repositories, shared documents, staging environments, ticket queues, or internal knowledge bases.

Typical use

Opening a pull request, updating staging content, changing a shared configuration file, or modifying a workflow used by other people.

Gate

Review ownership. A human owner approves the final state, not just the idea that the agent may try.

Deploy, migrate, or notify externally

Allowed: Trigger deployment steps, run migrations, publish content, send messages to external recipients, or perform actions that are visible outside the immediate team.

Typical use

Deploying a static site, publishing release notes, running a staging-to-production promotion, or sending approved stakeholder communications.

Gate

Explicit approval packet. Include diff, validation evidence, rollback path, recipients or targets, and the human approver.

Production, privileged, or destructive action

Allowed only by exception: Delete data, rotate credentials, change IAM, alter production infrastructure, modify billing, touch customer data, or perform irreversible actions.

Typical use

Rarely appropriate for autonomous execution. The agent can prepare commands, checklists, validation steps, and rollback notes, but a human should own the action.

Gate

Break-glass controls. Require named approvers, change record, monitoring plan, rollback trigger, and post-action review.

Every rung needs a control bundle.

Permission is not just “yes” or “no.” It is a bundle of boundaries: who owns the action, where the agent can work, what tools it can use, what evidence it must produce, and when it must stop.

IdentityWhich user, service account, or agent identity is performing the action?
ScopeWhich files, repos, systems, branches, environments, and records are in bounds?
ToolsWhich commands, APIs, MCP servers, connectors, and write actions are allowed?
DataWhat can the agent read, quote, transform, retain, export, or send elsewhere?
EvidenceWhat logs, diffs, tests, screenshots, or checks prove the action is safe enough?
Stop pointWhere does the agent pause for approval before impact becomes real?

Map the rung to the work, not to the ego.

A senior engineer may still use low-rung automation for high-risk work. A beginner may safely use higher-rung automation for low-risk drafts. The right rung follows blast radius, reversibility, sensitivity, and observability.

Situation Good default rung Why Approval evidence
Summarizing logs, docs, or source files L0-L1 Mostly read-only analysis, but the agent should still identify source limits and uncertainty. Source list, summary, assumptions, and open questions.
Creating a new standalone educational HTML page L2-L3 Generated artifact work is usually safe when paths are explicit and the index or production files are untouched. File path, preview, validation, and confirmation that forbidden files were not changed.
Editing application code in a branch L3-L4 The agent can work in a fenced branch, but tests and human review remain the gate before merge. Diff, test results, changed files, risk notes, and rollback plan.
Opening a pull request or updating a ticket L5-L6 The action affects shared systems, so the agent needs clear wording, target, and evidence before posting. PR body, ticket text, linked evidence, reviewers, and scope summary.
Terraform, IAM, database, or deployment work L1-L4 until approved Planning and local validation are useful, but execution can affect infrastructure, access, cost, or data. Plan output, blast radius, approvals, rollback, monitoring, and exact command list.
Production changes, destructive operations, or customer-impacting messages L7-L8 by exception These actions require named human ownership because mistakes escape the sandbox quickly. Change record, named approver, deployment window, rollback trigger, and post-action review.

Patterns that keep agents useful without turning them loose.

The ladder works best when the agent instructions, repository guidance, MCP tools, and approval workflow all describe the same boundary. Otherwise the agent gets one map from the repo, another from the chat, and a third from the tool permissions. That is how the little forklift finds the chandelier aisle.

A

Default low, elevate intentionally

Start at read, explain, and propose. Move upward only when the task, workspace, allowed tools, and stop point are explicit.

B

Separate planning from execution

The same agent can help write the plan and carry out a phase, but it should not invent the phase boundary while executing it.

C

Prefer narrow tools

A tool that can only create a draft is safer than a tool that can send, delete, label, archive, and forward everything in the mailbox.

D

Treat secrets as non-negotiable

The agent should not print secrets, transform secrets into logs, commit secrets, or move secrets into generated artifacts.

Common anti-patterns.

Most permission failures are not cinematic robot uprisings. They are boring shortcuts wearing a fake mustache: vague scope, broad tools, missing logs, skipped review, and “just this once” production access.

The permanent admin token

Giving an agent broad credentials because one workflow needed one powerful action creates durable risk. Prefer short-lived, task-specific authority.

The invisible command

Letting an agent run commands without showing what ran and what changed removes the evidence humans need to review the result.

The “fix everything” branch

Large unbounded rewrites are hard to review and easy to regret. Keep agent work sliced into small, named, reversible changes.

The merged assumption

An agent may infer missing context and keep moving. Permission to edit should not include permission to decide unclear requirements.

The tool buffet

Too many available tools blur the difference between “can help” and “can impact.” Tool exposure should match the job, not the inventory.

The absent stop sign

If instructions do not say where to stop, the agent may continue from draft to edit to command to publish. Put the stop point in writing.

Artifacts that make the ladder real.

The ladder should appear in the places agents actually read and humans actually review. A policy hidden in a wiki nobody opens is a decorative smoke alarm.

1

AGENTS.md

Define repo-level behavior: allowed paths, forbidden paths, command policy, validation expectations, stop conditions, and escalation rules.

2

PLAN.md

Describe the selected approach, phases, owners, non-goals, validation, rollback, and which permission rung each phase requires.

3

RUNBOOK.md

Capture exact commands, expected outputs, monitoring checks, rollback triggers, and human approval points for operational work.

4

MCP tool manifests

Expose narrow tools with clear descriptions, least-privilege scopes, confirmation requirements, and audit-friendly outputs.

5

Pull request template

Require a summary, changed files, risk level, test evidence, screenshots when useful, and a statement of what the agent did not touch.

6

Change record

For higher rungs, record the approver, target environment, execution window, rollback plan, and post-change verification.

Reusable permission check prompt

Use this before giving an agent more authority. It forces the work to name its rung, fence, tools, proof, and stop point.

Before taking action, classify this task on the Agent Permissions Ladder. Return: 1. Recommended rung and why. 2. Allowed files, systems, tools, and commands. 3. Forbidden files, systems, tools, and commands. 4. Data sensitivity and secret-handling rules. 5. Required validation evidence. 6. Human approval point before the next rung. 7. Rollback or recovery notes if the action fails. Do not execute, publish, deploy, send, delete, merge, or modify shared systems unless that action is explicitly approved.

Field guide takeaway: An agent permissions ladder turns autonomy from a giant glowing launch button into a set of deliberate rungs. Let agents read, reason, draft, edit, validate, and act only inside the authority they have been given, with clear fences, visible evidence, stop points, and human ownership before the work can affect shared systems, production environments, people, money, or data.
