AI Coding Agents

AI coding agents can read repositories, edit files, run commands, and summarize results. That power is useful only when the agent works inside explicit boundaries: scoped access, allowed commands, protected files, stop points, validation, and human review before merge or deployment.

What makes an agent different from chat?

A chat assistant mostly gives advice, drafts text, or explains code. A coding agent can take action inside a workspace. It may inspect files, modify source code, install or run tooling, generate tests, and produce a diff. That turns prompting into controlled delegation. The question is no longer only “is the answer good?” It becomes “what did it touch, what did it run, what changed, and who approved the result?”

The practical rule

Treat an AI coding agent like a junior contractor with a fast keyboard, uneven memory, and no authority to approve its own work.

Useful agent work has a fenced scope, a visible diff, repeatable validation, and a human owner.

The agent power map

Before using an agent, identify which powers it has. Each power is useful. Each one is also a tiny door in the wall.

R

Repository reading

The agent may search code, docs, config, tests, and history. Useful for understanding conventions, but risky if secrets, private data, or unrelated repositories are visible.

E

File editing

The agent may create, patch, rename, or delete files. Require scoped tasks, protected paths, and reviewable diffs so “helpful cleanup” does not become a surprise rewrite.

$

Command execution

The agent may run tests, builds, formatters, package managers, scripts, or shell commands. Separate safe validation commands from commands that mutate data, credentials, infrastructure, or dependencies.

P

Permission boundaries

The agent should use the least access needed for the current task. Write access, environment variables, network access, cloud credentials, and production tokens are not casual conveniences.

S

Stop points

The agent should stop before risky actions: destructive commands, migrations, secret handling, production changes, dependency upgrades, auth changes, billing logic, and public release steps.

V

Validation and review

The agent can run checks, but it does not approve the result. Humans review intent, diff, tests, side effects, missed requirements, and whether the work should proceed.

The controlled agent loop

Use this rhythm when the agent is allowed to edit files or run commands. The stop is part of the work, not a polite afterthought.

Assign one bounded task

Name the goal, allowed files, forbidden files, expected output, and whether the agent may edit or only inspect.

Inspect before editing

Require the agent to read relevant conventions, tests, existing patterns, and instructions before touching the code.

Patch the smallest slice

Ask for a narrow diff that solves the assigned problem without unrelated refactors, style churn, or architectural fan fiction.

Run allowed validation

Use known-safe commands first: syntax checks, linting, unit tests, build checks, snapshots, dry runs, or local smoke tests.

Stop and report

Make the agent summarize changed files, commands run, assumptions, test results, risks, and what still needs human review.

Human reviews the gate

A person decides whether to revise, approve, merge, deploy, or hand the agent the next bounded task.

Good agent instructions include

Give the agent enough structure to work quickly without inventing its own operating model.

  • The exact repository, branch, task, and phase to work on.
  • Files or directories it is allowed to inspect and edit.
  • Files or directories it must not touch without approval.
  • Commands it may run automatically, such as tests or format checks.
  • Commands that require a stop and explicit human approval.
  • Expected deliverable: diff, explanation, test results, PLAN.md update, or runbook change.
  • Review format: changed files, validation performed, assumptions, risks, and next suggested step.

Agent danger zones

These are not always forbidden, but they should never be accidental side quests.

  • Secrets, tokens, credentials, environment files, and private keys.
  • Authentication, authorization, role checks, admin logic, or permission models.
  • Database migrations, destructive queries, data repair scripts, and schema rewrites.
  • Billing, payments, donations, refunds, finance, or pricing workflows.
  • Infrastructure, Terraform, cloud resources, deployment scripts, and production config.
  • Dependency upgrades, lockfiles, generated code, and large formatting-only diffs.
  • Public-facing pages, forms, email senders, webhook receivers, and user communications.

Stop points: when the agent must pause

Stop points are pre-approved brakes. They prevent the agent from crossing from “local work” into “real consequence” while everyone is still admiring the tiny parade of green checkmarks.

Agent wants to... Stop because... Human should check...
Run a destructive command, delete files, or reset state. Recovery may be harder than the change looks. Backup, branch state, file scope, rollback path, and whether a safer command exists.
Change auth, admin roles, permissions, or access checks. Small logic changes can become security incidents. Threat model, least privilege, tests for allowed and denied cases, and reviewer ownership.
Touch secrets, environment files, tokens, or credentials. Prompts, logs, diffs, and command output can leak what should stay sealed. Approved secret path, redaction, rotation plan, and whether placeholders are enough.
Run migrations or data scripts. Data changes are often harder to reverse than code changes. Dry run, backup, migration ordering, rollback script, staging result, and audit trail.
Upgrade dependencies or regenerate lockfiles. The diff may hide transitive behavior changes. Why the upgrade is needed, security notes, compatibility, test coverage, and release risk.
Deploy, publish, send, merge, or open a production pull request. The agent is crossing from workspace activity to organizational action. Approval owner, validation evidence, release notes, rollback, and communication plan.

Reusable agent prompt

You are working in this repository as an AI coding agent.

Task:
Implement [specific bounded task] only.

Before editing:
- Inspect the relevant files and existing conventions.
- Identify the files you expect to change.
- Do not touch protected paths: [list paths].

Allowed:
- Read relevant source, tests, docs, and configuration.
- Edit only files required for this task.
- Run these validation commands: [list commands].

Stop and ask before:
- Running destructive commands.
- Changing auth, permissions, secrets, migrations, dependencies, infrastructure, billing, public forms, or deployment behavior.
- Implementing anything outside this task.

When finished, stop and report:
- Files changed.
- Commands run and results.
- Assumptions made.
- Risks or incomplete areas.
- What a human should review before merge.

Review the agent, not just the output

An agent can make code look tidy while quietly changing the agreement. Review both the patch and the path it took to get there.

IntentDoes the diff solve the assigned task, or did it wander into adjacent wishes?
ScopeAre touched files expected, minimal, and explainable?
BehaviorDid existing behavior remain intact unless the task explicitly changed it?
ValidationWere the right checks run, and are the results credible?
SecurityDid it avoid secrets, unsafe logging, broad permissions, and hidden trust changes?
DataDid it avoid destructive data changes, schema drift, and unapproved migrations?
OperationsIs there a rollback path, observability, and a clean deployment boundary?
CommunicationCan a human explain what changed, why, and what remains uncertain?

Agent maturity ladder

Teams do not need to begin with full automation. Start where the blast radius is tolerable, then earn broader access through repeatable controls.

Level Agent role Typical use Required control
Observe Reads and explains. Code walkthroughs, log summaries, architecture notes, test suggestions. No write access. No secrets. Human verifies claims.
Draft Suggests patches or files. Tests, docs, small bug fixes, examples, refactor proposals. Human applies or reviews patch. Agent cannot merge.
Edit Writes to a workspace branch. Bounded tasks with validation commands and a required stop report. Protected paths, allowed commands, code review, and CI gate.
Operate Uses approved workflows around real systems. Runbooks, dry runs, staging changes, controlled remediation. Explicit approvals, audit logs, rollback, and separation from production authority.
Field guide takeaway: AI coding agents are not magic interns hiding in the repository walls. They are fast, literal, and occasionally overconfident tools that need a work order, a fenced workspace, allowed commands, stop points, validation evidence, and human ownership before the result becomes real.
