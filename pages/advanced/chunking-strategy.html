Chunking Strategy

Chunking is the quiet machinery behind retrieval. It decides how documents are sliced before search, summarization, citation, and agent reasoning ever begin. Done well, it gives the model useful evidence with enough surrounding meaning. Done badly, it feeds the model shredded confetti and asks it to assemble a legal brief from the breeze.

Boundaries before bytes Metadata carries memory Retrieval quality starts upstream

What chunking really controls

Chunking is not just “split every 800 tokens.” It controls which ideas stay together, which headings survive, which permissions attach to content, and whether retrieved evidence is specific enough to answer the question.

Meaning boundaries

A chunk should preserve a complete unit of meaning: a policy clause, a troubleshooting step, a procedure, a Q&A entry, a code function, or a table row group. The goal is not equal-sized bricks. The goal is answerable fragments.

Retrieval precision

Large chunks can bury the answer inside irrelevant material. Tiny chunks can retrieve a sentence without the rule it depends on. Good chunking gives search a clean target and gives the model enough context to avoid guessing.

Signal densityQuestion fitNoise control

Governance inheritance

Chunks need to carry access rules, source ownership, freshness, sensitivity labels, and version information. A chunk without metadata is a library card with the title rubbed off and the return date on fire.

OwnerVersionAccess scope

Answer traceability

When a system cites sources, it usually cites retrieved chunks. If chunks mix unrelated topics, outdated sections, or fragments from multiple documents, the citation trail becomes muddy even when the model sounds confident.

CitationsEvidenceAuditability

The wrong cut changes the answer

Chunking is an architectural decision, not a clerical one. The same document can become useful evidence or retrieval soup depending on where the cuts happen.

Weak chunk

Split by raw length only

The system cuts every fixed number of tokens without respecting headings, examples, tables, or policy sections. A retrieved chunk may contain the end of one rule, the start of another, and no clue which one applies.

Chunk 014“...except where approval is required. Employees may use external AI tools for drafts. Confidential customer information must not be entered...”
ProblemThis looks useful, but it hides the policy title, approval condition, sensitivity category, owner, and effective date.
Strong chunk

Split by reusable meaning

The system keeps a complete policy rule with its heading, scope, exceptions, source metadata, and neighboring context. Retrieval can now return evidence that is narrow enough to cite and complete enough to trust.

Policy · External AI Tools · Confidential Data · v2026.04“Do not enter confidential customer information into external AI tools unless the tool is approved for that data classification and the use case has documented authorization.”
Why it worksThe rule, scope, classification, version, and ownership travel together instead of arriving as a mysterious sentence shard.

Choose chunks by source shape

Different source types need different cuts. A universal chunk size is tempting because it feels tidy. It is also how a knowledge base turns into a blender with a login screen.

Policies and standards

Chunk by section, clause, exception, and approval condition. Preserve definitions, effective dates, owner, version, jurisdiction, and links to parent policy. Avoid separating a rule from its exception.

Clause-awareVersionedException-safe

Runbooks and procedures

Chunk by task or troubleshooting path. Keep prerequisites, commands, expected results, rollback steps, and escalation notes together. A single command without its “when not to run this” note is a tiny operational goblin.

Task-levelRollbackEscalation

Tickets and incidents

Chunk by event, decision, investigation thread, timeline segment, or resolution. Preserve timestamps, systems, severity, people, and status. Separate noisy commentary from confirmed facts.

TimelineDecision logFact status

Code repositories

Chunk by file, function, class, module, interface, and nearby tests. Include path, language, imports, ownership, and dependency hints. For generated answers, code chunks should help locate the real artifact, not pretend to be the whole system.

Path-awareFunction-levelTests nearby

Tables and spreadsheets

Chunk by logical row groups, not screen pages. Preserve column names, units, filters, sheet names, formulas, and date ranges. For numeric work, retrieval should surface the data shape before the model starts arithmetic theater.

Column headersUnitsFormulas

Slide decks and visuals

Chunk by slide, speaker note, figure, chart, and caption. Preserve slide title, visual description, nearby callouts, and deck section. A chart without axis labels is not evidence. It is decorative fog.

Slide-awareChart labelsCaptions

A practical chunking workflow

Start with the questions the system must answer, then design chunks that make those answers findable, citeable, and governable.

Map use cases

List the expected questions, decisions, and workflows. “Find a password reset step” and “summarize compliance obligations” need different cuts.

Identify source anatomy

Detect headings, tables, code blocks, timestamps, owners, document types, and access labels before chunking. Structure is retrieval fuel.

Define boundaries

Choose semantic boundaries first, then set size limits and overlap rules. Let meaning drive the knife, not the token counter.

Attach metadata

Carry document title, path, owner, version, date, sensitivity, audience, and authority level. Metadata is the chunk’s passport.

Evaluate retrieval

Run test questions. Check whether the top results include the right rule, the right context, and the right source, not merely similar words.

Refresh and retire

Rebuild chunks when source documents change. Remove stale chunks, duplicate chunks, and orphaned fragments before they become ghost evidence.

Common failure modes

Most retrieval failures are blamed on the model. Some deserve that blame. Many start earlier, when the knowledge was sliced into pieces the system could not reason over.

Fragment drift

A chunk contains the middle of an idea but not the framing. The model sees a sentence that looks decisive, then answers without the condition, exception, or warning that came before it.

Missing setupLost exception

Context bloat

Chunks are so large that retrieval returns documents instead of answers. The model must sift through unrelated material, which increases cost, lowers precision, and invites confident mush.

High noiseLow precision

Metadata starvation

The text is retrieved, but the system does not know who owns it, when it was updated, what it applies to, or whether the user may see it. That is not knowledge. That is a loose page in a windy parking lot.

No ownerNo freshness

Duplicate swarm

Multiple copies of near-identical content crowd out better evidence. Old exports, copied pages, and stale PDFs can dominate retrieval unless deduplication and source priority are explicit.

DuplicatesSource priority

Table shredding

Tables are split without headers, units, or row relationships. The model retrieves numbers but not what they measure. This is how “12” becomes a percentage, a dollar amount, or a raccoon-sized mystery.

Lost headersLost units

Permission bleed

Chunks inherit broad access because the ingestion system did not preserve document, folder, row, or field-level restrictions. Retrieval should never turn private context into public convenience.

Artifacts worth keeping

A chunking strategy should leave behind operational evidence. Not just a pipeline that runs, but a map of why the cuts were made and how they will be checked.

Chunking policy

Defines chunk boundaries, size ranges, overlap rules, metadata requirements, source priorities, and exceptions by document type.

Retrieval test set

A set of realistic questions with expected source documents, acceptable chunks, and known traps. This catches regressions when ingestion changes.

Source inventory

A list of indexed sources with owners, update cadence, authority level, sensitivity, and whether each source is canonical, supplemental, or deprecated.

Metadata contract

A required schema for every chunk. This makes filtering, citations, access control, retention, and freshness checks possible.

Failure review log

A lightweight record of bad answers, missed retrievals, stale evidence, duplicate problems, and whether the fix belongs in chunking, indexing, prompting, or source cleanup.

Refresh plan

A schedule and trigger model for re-indexing. Important sources should refresh when they change, not whenever someone remembers the knowledge base exists.

Field guide takeaway: Chunking strategy is where retrieval quality is quietly won or lost. A good system does not merely chop documents into token snacks. It preserves meaning, carries metadata, respects permissions, retires stale fragments, handles source types differently, and proves through retrieval tests that the right evidence appears before the model starts talking.
