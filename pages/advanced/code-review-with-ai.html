Code Review with AI

AI can widen review coverage, spot boring omissions, and ask useful second-reader questions. It must not become the merge button, the accountable reviewer, or a comforting silence machine wearing a tiny rubber stamp.

AI expands coverage Humans own approval Silence is not safety Evidence beats vibes

The useful mental model

Treat AI as an extra reviewer with unusual stamina and imperfect judgment. It can read diffs patiently, compare code against stated requirements, generate test ideas, and notice inconsistency. It cannot accept responsibility for the release.

AI can say “look here.” Only an accountable human can say “ship it.”

The review stack

AI review works best when it is one layer in a review system, not a shiny replacement for the system.

Where AI helps in review

Good AI review is targeted. Ask the model to inspect named risks instead of saying “review this” and accepting whatever confetti falls out.

Δ

Explain the diff

Ask AI to summarize what changed by file, component, endpoint, migration, or behavior. This helps reviewers find the story before they inspect the machinery.

✓

Compare against intent

Give the AI the ticket, PLAN.md phase, acceptance criteria, or bug report. Ask whether the diff actually matches the requested work or wanders into decorative shrubbery.

?

Generate review questions

Use AI to produce specific questions for the human reviewer: missing test cases, unclear assumptions, compatibility concerns, and places where business rules may be implicit.

T

Find test gaps

Ask what behavior appears untested, which edge cases deserve coverage, and whether the validation commands actually prove the claim being made.

🔒

Spot security smells

Have AI look for secrets, over-broad permissions, unsafe deserialization, injection risks, missing authorization checks, dangerous logging, and trust-boundary confusion.

!

Flag uncertainty

Require the AI to separate confirmed issues from suspicions. A confident false alarm is still a false alarm, just wearing a louder jacket.

The AI-assisted review loop

This loop keeps AI review grounded in evidence instead of becoming a theatrical nod from a very articulate parrot.

State the intent

Provide the ticket, phase, acceptance criteria, bug report, design note, or expected behavior before asking for review.

Limit the scope

Name the files, diff, commit range, or pull request area. Tell AI what not to review if the scope is intentionally narrow.

Ask for categories

Separate correctness, tests, security, maintainability, compatibility, performance, observability, and documentation.

Demand evidence

Require file names, functions, line references, commands, or exact behavior. No ghost-bugs drifting through the attic.

Verify findings

Humans check whether the AI’s concern is real. Run tests, inspect code, reproduce behavior, or reject the issue clearly.

Keep ownership

The reviewer records what was checked, what was accepted, what was dismissed, and why the final decision is safe enough.

Use AI for

These are the high-value tasks where AI acts like a tireless second set of eyes.

  • Summarizing large diffs so reviewers can orient quickly.
  • Checking whether the change matches the stated requirement or PLAN.md phase.
  • Looking for missing tests, unhandled edge cases, and inconsistent error handling.
  • Reviewing compatibility risks across old and new behavior.
  • Drafting focused reviewer checklists for humans to confirm.
  • Explaining unfamiliar code paths before a human reviewer makes a decision.

Do not use AI for

This is where the danger goblin gets a clipboard and starts making promises it cannot keep.

  • Replacing required human approval on production-impacting changes.
  • Treating “no issues found” as proof that the change is safe.
  • Approving changes to security, IAM, payment, data deletion, migrations, or public workflows without accountable review.
  • Reviewing code without giving the AI the actual intent, constraints, or acceptance criteria.
  • Accepting suggested fixes without understanding the tradeoff they introduce.
  • Letting AI create broad refactors inside a review that was supposed to be about a small change.

Review focus matrix

Review area Ask AI to check Human must confirm
Correctness Does the implementation match the described behavior, input rules, error cases, and acceptance criteria? Whether the requirement itself is understood correctly and whether the chosen behavior is acceptable.
Tests Which paths, edge cases, regression cases, and failure modes appear untested? Whether the test suite actually runs, fails when it should, and proves enough for the risk level.
Security Are secrets exposed, permissions broadened, auth checks missing, or untrusted inputs mishandled? Whether findings are real, whether policy applies, and whether the risk is acceptable to merge.
Data and migrations Are rollback, coexistence, defaults, null handling, and destructive operations addressed? Whether the migration path is safe for real data and whether operational timing is acceptable.
Operations Are logging, metrics, alerts, feature flags, and failure visibility sufficient? Whether responders can detect, diagnose, and recover from the change in the real environment.
Maintainability Does the code violate local conventions, duplicate logic, hide complexity, or require documentation? Whether the tradeoff is worth it given team standards, deadlines, and future maintenance cost.

Reusable review prompt

Use this when the AI can see the diff and the relevant intent.

Focused AI review

Review this change against the stated intent and acceptance criteria.

Do not approve or reject the change.  Act as an additional reviewer.

Check for:
- correctness gaps
- missing tests
- security or permission risks
- data or migration risks
- compatibility with existing behavior
- operational visibility gaps
- unclear assumptions
- unrelated changes or scope creep

For every finding, include:
- severity: blocker, important, minor, or question
- evidence from the diff or files
- why it matters
- what a human reviewer should verify

If you do not see enough context, say what is missing instead of guessing.
