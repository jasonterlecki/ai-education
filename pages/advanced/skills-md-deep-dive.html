The important naming wrinkle

Teams often say “SKILLS.md” when they mean the skills layer. In many agent systems, the actual reusable unit is a folder containing a singular SKILL.md manifest plus optional supporting files.

1

SKILLS.md as the catalog idea

Useful as a mental model for a collection of repeatable capabilities: code review, Playwright testing, release notes, docs cleanup, Terraform review, or migration planning.

2

SKILL.md as the working unit

The agent usually activates one skill at a time by reading a skill folder’s manifest, instructions, and optional files. The skill is a pocket workshop, not a second repository constitution.

Core rule

Put always-on repository behavior in AGENTS.md. Put reusable, task-specific procedure in a skill. Put external system access in MCP. Put temporary task detail in the prompt. This separation keeps the agent’s brain from becoming a backpack full of bricks.

What a skill should contain

A good skill is small enough to trigger cleanly, specific enough to guide action, and structured enough that the agent can execute the same workflow twice without asking the universe to improvise.

A

Manifest

The name and description tell the agent when the skill should wake up. The description is the little lighthouse, so vague descriptions sink ships.

B

Procedure

The main instructions explain the sequence: inspect, plan, act, validate, report. They should contain gates, stop conditions, and proof requirements.

C

References

Longer docs belong in references, not in the first screen of the skill. Keep the manifest light and let the agent open deeper material only when needed.

D

Scripts

Repeatable commands, validation helpers, formatters, and report generators can live with the skill. Scripts turn “remember the ritual” into “run the ritual.”

E

Assets

Templates, sample prompts, checklists, starter files, and visual resources can travel with the skill so the output stays consistent across sessions.

When to create a skill

Create a skill only when a workflow is reusable, bounded, and teachable. A skill is a bridge, not a junk drawer with YAML confetti.

Good trigger

The task repeats

You keep asking for the same review shape, migration checklist, test loop, release note format, or document transformation. Repetition is the smoke signal.

Good trigger

The workflow has steps

The agent should not just “write something.” It should inspect inputs, choose a path, produce work, validate it, and report evidence.

Good trigger

The skill has reusable artifacts

If the work needs templates, examples, commands, test data, or reference docs, a skill folder is cleaner than stuffing everything into AGENTS.md.

Good trigger

The boundary matters

A skill can say when to use it and when not to use it. That prevents the agent from using a chainsaw to slice toast.

Good trigger

Multiple repos need it

Skills are useful when one practiced workflow should travel across projects without copying a wall of instructions into every repo.

Good trigger

Quality depends on consistency

If inconsistent output causes review friction, encode the pattern. The skill becomes a mold for reliable work instead of a hopeful incantation.

What not to put in a skill

The wrong skill makes agents more confident and less correct. That is not automation. That is a tiny paperwork dragon with a keyboard.

Bad fit Why it causes trouble Better home
Always-on repo rulesBuild commands, test commands, coding standards, review expectations. Skills are conditional. Critical repo rules should load before every task. AGENTS.md, closest directory guidance, or repo docs referenced by AGENTS.md.
One-off task detailTemporary instructions for today’s specific bug, page, feature, or branch. Skills persist beyond the task and can accidentally fossilize old assumptions. The prompt, a temporary PLAN.md, or a task-specific issue comment.
Secrets and credentialsTokens, passwords, private keys, cookie values, or production-only access notes. Skills are reusable files. Reusable files are a terrible hiding place for secrets. Secret managers, environment configuration, and explicit runtime access controls.
Broad philosophy“Write good code,” “be careful,” “think deeply,” or “make it professional.” Vague guidance burns context without changing behavior. Concrete acceptance criteria, checklists, examples, and validation commands.
External access permissionsRules for calling GitHub, Jira, Slack, cloud APIs, or internal systems. A skill can explain a workflow, but it should not pretend to grant safe access. MCP configuration, admin policy, sandbox settings, and approval gates.

Skill activation: the three-layer mental model

Write skills so the agent can find the right one cheaply, read the procedure only when relevant, and fetch heavy references only when the task earns them.

1

Billboard layer

The name and description advertise the trigger. Mention the task, key nouns, and limits early because this is often what matching sees first.

2

Playbook layer

The SKILL.md body gives the standard operating procedure: inputs, steps, constraints, validation, and final reporting format.

3

Supply kit layer

References, scripts, and assets stay nearby but unloaded until useful. This keeps token use disciplined while preserving depth.

AGENTS.md vs skills vs MCP vs prompt

These tools overlap only if you blur their job descriptions. Keep each one crisp and the agent gets less fog and more compass.

G

AGENTS.md

Use for: durable repo behavior. How to build, test, lint, review, and respect local conventions.

S

Skill

Use for: reusable workflows. A bounded playbook with optional scripts, examples, templates, and references.

M

MCP

Use for: external capabilities. Tools and systems the agent can call through explicit, governed interfaces.

P

Prompt

Use for: the immediate mission. The goal, context, constraints, files, and definition of done for this task.

A practical SKILL.md skeleton

Start small. A clear trigger plus a tight procedure is better than a sprawling masterwork nobody wants to read, including the agent.

example-skill/SKILL.md minimal pattern 
---
name: release-note-review
description: Review release notes for missing user impact, risk, rollback notes, owner, evidence, and unclear claims.  Use this when release notes or changelog entries need quality review before publication.
---

# Release Note Review Skill

## Use when
- The user asks to review release notes, changelog text, launch notes, or customer-facing release summaries.
- The task is about quality, clarity, risk, and publication readiness.

## Do not use when
- The user asks to write code, debug a defect, or summarize a meeting.
- The release details are missing and the user only wants brainstorming.

## Inputs to inspect
- Release note draft.
- Linked issue, PR, ticket, or deployment notes when provided.
- Audience and publication channel if known.

## Procedure
1. Identify the audience and promised change.
2. Check whether the note explains user impact, risk, rollout, rollback, owner, and support path.
3. Flag unsupported claims or invented certainty.
4. Suggest precise edits without adding facts that are not present.
5. Produce a pass/fail readiness summary.

## Output
- Readiness verdict.
- Highest-risk gaps first.
- Suggested replacement text only where safe.
- Questions that must be answered before publication.

Why this pattern works

The description contains the trigger words the agent needs. The body says when to use the skill, when to avoid it, what to inspect, what to do, and how to report. It is procedural without pretending to know project facts.

✓
BoundedIt handles release note review, not every communication task.
✓
Evidence-awareIt tells the agent to inspect sources and avoid invented certainty.
✓
ReviewableIt produces a verdict, gaps, safe edits, and questions.

Skill folder structure

Keep the folder legible. The agent should be able to understand what is essential, what is optional, and what is heavy reference material.

Keep weight off the manifest

The first file should not be an encyclopedia. Put core procedure in SKILL.md, then move long examples, policy references, templates, and helper commands into subfolders. This lets the skill stay discoverable without forcing every detail into context immediately.

SKILL.mdInstructions and metadata. This is the cockpit.
2
referencesLonger material the agent should open only when it needs more evidence.
3
scripts and assetsRepeatable helpers and reusable output shapes.

Skill quality checklist

Before trusting a skill, review it the way you would review an internal runbook: clear triggers, safe boundaries, observable output, and no secret trapdoors.

✓

Trigger clarity

The description names the task, the artifacts, and the exact moment the skill should activate. It also implies when not to use it.

✓

Bounded authority

The skill tells the agent what to do, not what it is allowed to access. Sensitive access stays governed elsewhere.

✓

Validation step

The skill requires proof: tests run, files checked, claims supported, output reviewed, or a stop condition reported.

✓

Output contract

The final response shape is explicit. This prevents the agent from returning a pretty fog bank instead of usable evidence.

✓

Token discipline

Long references are externalized. The skill reads like a launch checklist, not a cargo manifest.

!

Safety review

No secrets, no production credentials, no blanket permission to deploy, and no instruction to skip human approval.

Decision guide: skill or something else?

When the instruction is homeless, use this small routing map before feeding it to the context furnace.

Every task in this repo? Put it in AGENTS.md.
Repeated bounded workflow? Create a skill.
Needs external system access? Use MCP plus policy controls.
Only true today? Keep it in the prompt or plan.

Anti-patterns that make skills brittle

A weak skill does not merely fail. It fails with confidence, laminate, and a tiny clipboard.

!

The mega-skill

One skill tries to handle testing, deployment, docs, review, security, and stakeholder updates. Split it before it becomes a warehouse fire.

!

The vague trigger

“Use this for quality work” is not a trigger. Use concrete nouns, file types, workflow names, and boundaries.

!

The authority leak

The skill tells the agent to deploy, delete, rewrite, email, or merge without approval. Skills guide work. They should not launder permission.

!

The stale ritual

The workflow changes but the skill does not. Old skills are fossilized process, and fossils make poor operators.

Field guide takeaway: A skill is a reusable procedure, not a dumping ground for every preference the team has ever had. Good skills teach agents how to perform a specific repeatable job, where supporting scripts and references live, what evidence proves success, and when the agent should stop because the situation no longer matches the recipe.
