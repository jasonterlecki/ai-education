Test-First AI Workflows

Before an AI coding agent changes code, define what correct behavior looks like, how it will be proven, and what must not move. A test-first workflow gives the agent a target instead of a fog bank with a keyboard.

Expected behavior first Validation before edits Reviewable proof, not vibes

Why test-first matters with AI agents

An AI agent can produce confident code faster than a human can review its assumptions. Tests, examples, fixtures, and acceptance checks turn the work from “looks plausible” into “we have evidence.”

🎯

The agent gets a target

Without expected behavior, the agent may optimize for style, convenience, or invented architecture. A test-first prompt tells it what success means before it starts moving furniture.

🧪

Review gets evidence

A reviewer should not have to guess whether the change works. The agent should show the test added or updated, the command run, and the exact result.

🧭

Drift becomes visible

When the implementation wanders away from the test, the mismatch is visible early. The test is the trail marker; the diff is the fox tracks in the snow.

The test-first loop

This loop works for coding agents, human developers using AI, infrastructure scripts, data transformations, API changes, form handling, and automation that needs controlled delivery.

Describe behavior

State the user-visible or system-visible behavior in plain language. Include normal cases, edge cases, and what must remain unchanged.

Choose proof

Decide how the behavior will be validated: unit test, integration test, dry run, fixture comparison, screenshot check, lint rule, smoke test, or manual checklist.

Add or update tests

Ask the agent to create the smallest test that captures the intended behavior. The test should fail or be incomplete before the implementation is changed.

Implement to the test

Let the agent change only the files needed to make the chosen proof pass. No unrelated refactors. No scenic detours through the entire repository.

Run, report, stop

The agent runs validation, reports changed files, commands, assumptions, failures, and remaining risks, then stops for review before the next slice.

The practical rule

Before an agent writes implementation code, make it explain what it will prove and how. The proof can be automated or manual, but it must be explicit enough for a reviewer to challenge.

Never let the first “test” be a surprised user, a broken deployment, or a production log screaming in lowercase.

Reusable prompt

Use a test-first workflow for this change.

Goal:
[Describe the behavior we need.]

Constraints:
- Do not implement unrelated refactors.
- Preserve existing behavior unless the goal explicitly changes it.
- Do not touch protected files.
- Keep the diff reviewable.

Before implementation:
1. Inspect the relevant code paths.
2. Identify the validation strategy.
3. Add or update the smallest useful test, fixture, smoke check, or manual checklist.
4. Explain what the proof covers and what it does not cover.

Then implement only what is needed to satisfy that proof.

When finished, stop and report:
- files changed
- tests or checks added
- validation commands run
- results
- assumptions made
- risks or remaining manual review items

Validation decision matrix

Change type Good first proof What to watch
Pure function, parser, formatter, calculator, or rules logic. Unit tests with representative inputs, boundary values, and failure cases. AI may test only the happy path. Require edge cases and clearly named examples.
API endpoint, controller, webhook, or form receiver. Request and response tests, validation failures, permission checks, and fixture payloads. Confirm authentication, malformed input, idempotency, and error messages are covered.
Database migration or data model change. Migration dry run, rollback test, schema assertions, seed data test, and compatibility check. Do not let the agent assume legacy data is clean, complete, or shaped like the new model.
UI or content workflow. Screenshot comparison, accessibility check, route smoke test, and manual acceptance checklist. Visual success is not functional success. Confirm forms, links, mobile layout, and empty states.
Infrastructure, CI/CD, permissions, or automation. Plan output, dry run, policy check, linting, and approval gate before any apply step. Require explicit blast-radius notes, rollback path, and confirmation of which environment is targeted.
Bug fix for production behavior. Regression test that fails before the fix and passes after it. Make sure the agent proves the original bug, not just a nearby invented bug-shaped decoration.

Review checklist before accepting the diff

A test-first workflow does not remove human accountability. It gives reviewers sharper tools, better evidence, and fewer fog creatures hiding in the corners.

Behavior named The expected behavior is written clearly enough that a non-author can review it.
Proof exists There is a test, check, dry run, screenshot, fixture, or checklist tied to the behavior.
Scope stayed fenced The agent did not refactor unrelated files, rename concepts, or “improve” architecture without permission.
Failures are visible Known gaps, skipped tests, flaky checks, and manual verification needs are documented.
Commands are repeatable The validation commands can be run again by a reviewer or in CI without decoding agent folklore.
Existing behavior protected Legacy paths, permission boundaries, public routes, data formats, and user workflows were not quietly broken.
Edge cases included Empty input, invalid input, missing permissions, duplicate requests, and boundary values were considered.
Next step is bounded The agent stopped with a clean summary before rolling into the next phase or inventing future work.
Field guide takeaway: Test-first AI work turns a coding agent from a confident improviser into a bounded collaborator. Define the behavior, choose the proof, implement the smallest slice, run the checks, and make the agent stop before the fog rolls back in.
