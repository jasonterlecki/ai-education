Tool Calling and Function Boundaries

Tool calling lets an AI system ask for real work to happen outside the model: search a system, query a database, calculate a value, write a draft, open a ticket, or call an API. The boundary matters because the model proposes intent, but the application owns execution, validation, authorization, logging, and consequences.

Tool contracts Function boundaries Action safety

Tool calling is a handoff, not a spell.

The model does not magically perform the operation by wanting it loudly. It emits a structured request. Your system decides whether that request is valid, safe, authorized, executable, and worth returning to the model.

01

The model is a planner and formatter

The model can choose a tool, fill arguments, explain why it needs the result, and interpret the output. It is good at turning messy language into a structured request, but it should not be the only authority deciding whether an action is allowed.

A tool call is a proposal with parameters. Treat it like input from a very fast junior operator who needs guardrails, not like a root commandment from the silicon mountain.
02

The application owns the real boundary

Your code, workflow engine, MCP server, or integration layer executes the operation. That layer must validate schemas, check permissions, redact sensitive output, log evidence, handle errors, and decide whether a human approval gate is required.

  • Models suggest tool calls.
  • Applications execute tool calls.
  • Humans own risky outcomes.

The standard tool call loop

A reliable tool workflow is a loop with visible handoffs. The dangerous version is a blur where the model thinks, acts, interprets, and mutates systems without anyone seeing the seams.

Advertise tools

The application tells the model which tools exist, what each tool does, and what arguments each tool accepts.

Model requests a call

The model selects a tool and returns structured arguments. This is not execution yet. It is a request.

Boundary checks

The application validates arguments, checks identity, applies policy, and asks for approval when the action has impact.

Tool executes

The application or server performs the operation, captures result metadata, handles errors, and avoids leaking sensitive data.

Model resumes

The result is returned to the model so it can summarize, choose another step, or produce the final answer.

Five boundaries every tool needs.

Tools are small doors into real systems. A good door has a label, a lock, a frame, a peephole, and a record of who went through it.

Capability boundary

What can this tool actually do? Read, search, calculate, draft, write, send, delete, deploy, purchase, or change access are different animals.

Argument boundary

What inputs are allowed? Use schemas, enums, path allowlists, size limits, safe URL rules, tenant checks, and typed parameters.

Authority boundary

Who is the action running as? Prefer per-user authorization, narrow scopes, short-lived tokens, and explicit approval for risky actions.

Data boundary

What can the tool reveal back to the model? Results should be filtered, summarized, redacted, and scoped to the task.

Evidence boundary

What gets logged? Capture tool name, arguments, caller, target, result status, approval state, and correlation IDs.

Design tools around verbs, not kingdoms.

The safest tools are boring and specific. The riskiest tools are broad, heroic, and suspiciously enthusiastic, usually with names like “manageEverything.”

✓

Narrow verb tools

Prefer tools such as search_ticket_titles, create_pull_request_draft, or run_readonly_plan. Narrow verbs make validation and approval easier.

?

Two-step write flows

Separate “prepare” from “apply.” The agent can prepare a draft, diff, ticket, migration plan, or command packet before a person approves execution.

!

Super-tool traps

A tool that accepts natural language and can touch broad systems becomes a policy swamp. Avoid tools that turn “do the thing” into unlimited action.

Common boundary failures.

Most tool accidents are not strange. They are normal software integration mistakes wearing AI goggles and a tiny cape.

A

Natural language as authority

The tool accepts a broad instruction like “fix the repo” and decides internally what to do. That erases the boundary between planning and execution.

B

Invisible defaults

The tool has hidden defaults for workspace, branch, tenant, environment, recipient, or destructive mode. The model cannot safely reason about what it cannot see.

C

Tool output as instruction

Retrieved content tells the model to ignore rules, open a link, reveal context, or call another tool. Tool output is data, not governance.

D

Missing audit seam

Humans cannot tell which tool ran, with which arguments, under whose authority, against which target, or why the result changed the final answer.

Where boundaries belong.

Do not put every safety rule in the prompt. Prompts are helpful, but tools need enforcement where execution happens.

P

Prompt boundary

Use the prompt to describe the task, non-goals, source materials, desired output, and stop condition. It frames the work but should not be the only safety barrier.

T

Tool boundary

Use tool schemas, validation, scoped credentials, redaction, and allowlists to enforce what the model can actually cause.

H

Human boundary

Use human review when impact leaves the sandbox: external messages, production changes, shared repos, money, identity, customer data, or irreversible actions.

Field guide takeaway: Tool calling is where AI stops merely describing work and starts touching systems through code you control. Keep the boundary explicit: the model may choose a tool and propose arguments, but the application must validate inputs, enforce permissions, redact outputs, log evidence, require approval for risky actions, and stop broad natural-language intent from becoming uncontrolled execution.
