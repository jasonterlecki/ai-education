AI-Generated Code Smells

AI can produce useful code quickly, but it also produces code that is fluent, plausible, and sometimes quietly wrong. The smell is not “AI touched this.” The smell is when the output looks finished before it has earned trust through context, tests, security review, and human ownership.

The first code smell is a clean answer with no evidence.

AI-generated code should be reviewed like a fast junior contributor with a neat formatter and a suspiciously confident grin. It may be correct, but it still needs context alignment, tests, edge-case analysis, dependency review, and security checks.

✓

AI code is not automatically bad

The useful posture is not suspicion theater. AI can speed up boilerplate, tests, docs, refactors, examples, and exploration. The reviewer’s job is to separate useful acceleration from hidden fragility.

!

AI code is not automatically done

A compiling answer can still miss business rules, misuse libraries, flatten error handling, skip authorization, invent APIs, create insecure defaults, or pass the happy path while leaving a little rake garden for production.

Review the claim, not the confidence.

The model’s fluency is not evidence. Evidence is a passing test, a checked diff, a verified API, a bounded change, a threat model, a migration plan, or a human reviewer who can explain why the result is safe enough.

Common AI-generated code smells

These smells appear because AI tends to optimize for a plausible completed artifact. Real systems require context, ugly constraints, old decisions, deployment reality, and the tiny goblins living behind every edge case.

Correctness

Invented API calls

The code uses methods, flags, fields, SDK behavior, or framework hooks that do not exist, existed in another version, or belong to a different library.

Review move: verify every unfamiliar call against the installed dependency version, not memory, vibes, or a blog from 2019.

Correctness

Happy-path tunnel vision

The code handles the clean example but misses empty inputs, duplicate records, partial failures, pagination, retries, timeouts, nulls, permissions, localization, and concurrency.

Review move: ask what must go wrong before this code becomes dangerous, noisy, or expensive.

Maintainability

Overbroad rewrite

The model changes surrounding structure, renames concepts, reformats unrelated files, or creates a new abstraction when a small patch was requested.

Review move: compare the diff to the requested scope. Extra cleverness pays rent only when it reduces future risk.

Testing

Tests that mirror the implementation

The tests reproduce the same assumptions as the generated code, mock away the risky behavior, or assert that the code did what it already does.

Review move: test behavior, boundaries, and failure modes. A test that only admires the code is a tiny applause machine.

Security

Input trust creep

The code accepts user, file, API, or tool output as safe because the generated example uses friendly data.

Review move: inspect validation, encoding, escaping, parameterization, authorization, path handling, and logging.

Security

Secret-shaped convenience

The code hardcodes sample tokens, prints environment values, commits placeholder credentials, or moves sensitive data into logs and exception messages.

Review move: check config loading, secret redaction, log output, fixtures, generated docs, and examples.

Architecture

Local patch, global side effect

A small change alters caching, retries, database queries, permissions, costs, message formats, or background jobs far from the edited file.

Review move: identify consumers, callers, queues, schemas, migrations, rollout sequence, and rollback path.

Architecture

Generic abstraction fog

The model creates helpers, factories, providers, adapters, managers, and interfaces before the system needs them.

Review move: keep the code boring until duplication and variation prove the abstraction has a job.

Delivery

No operational story

The code works in the editor but says nothing about deployment, metrics, feature flags, migration order, data backfill, monitoring, or rollback.

Review move: require operational notes when the change can affect production behavior, cost, data, or users.

The reviewer’s AI-code loop

Review is not a single stare at a diff. It is a loop that moves from intent to evidence, because the problem with AI code is often not syntax. It is unverified fit.

Recover the intent

What was the code supposed to accomplish, and what was explicitly out of scope?

Inspect the diff

Which files changed, which files should not have changed, and what hidden behavior changed with them?

Challenge assumptions

What inputs, states, versions, permissions, and failures did the code silently assume?

Validate evidence

Which tests, linters, scanners, builds, manual checks, or traces prove the change is safe enough?

Decide the gate

Merge, request changes, split the patch, add tests, or stop because the requirement itself is unclear.

Smell-to-action matrix

Do not just label a smell. Route it to the next useful review action, otherwise the finding becomes a decorative sticky note.

Signal Likely cause Reviewer action Gate
Large diff for a small request Model optimized for a complete-looking solution instead of a minimal safe change. Ask for a scoped patch, separate refactors, and preserve unrelated formatting. Split or shrink
New dependency appears The model chose convenience over supply-chain discipline. Review license, maintenance, vulnerability history, alternatives, and whether built-in tools are enough. Security review
No tests changed The model treated implementation as completion. Require behavior tests, regression tests, or an explanation of why existing tests cover the change. Evidence needed
Permission, auth, or data paths touched The generated code may have crossed a security boundary without naming it. Review authorization, identity, tenant boundaries, logging, redaction, and abuse cases. High scrutiny
Clean code, unclear requirement The model filled ambiguity with plausible behavior. Return to acceptance criteria before polishing the implementation. Clarify first
Tests pass only with broad mocks The risky integration was simulated away. Add at least one realistic integration, contract, or boundary test. Prove behavior

Reviewer artifacts that keep the work honest

Artifacts turn “I looked at it” into review evidence. They also make it easier to spot when an agent wandered off-task and came back carrying a suspiciously shiny abstraction.

D

Diff summary

List changed files, intended behavior change, accidental-looking changes, and what was deliberately not touched.

T

Test evidence

Capture commands run, test scope, failures, skipped tests, manual checks, and why the evidence matches the risk.

S

Security notes

Record input boundaries, auth checks, secrets handling, dependencies, output encoding, and data exposure risk.

R

Rollback note

Explain how to revert, disable, feature-flag, roll back migration, or restore old behavior if the change misbehaves.

A

Assumption ledger

Name assumptions the generated code depends on: version, schema, permissions, data shape, traffic, cost, or operational behavior.

O

Owner approval

Identify who is accountable for accepting the behavior, not just who asked the model to generate it.

Reusable review prompt

Use this to review AI-assisted code before it becomes a pull request, merge candidate, or production change.

Review this AI-generated or AI-assisted code for code smells and acceptance risk. Invented APIs, version mismatches, or dependency assumptions. 3. Missing edge cases, failure modes, pagination, retries, nulls, and concurrency risks. 4. Security risks: input validation, authorization, injection, secrets, logging, dependencies, and output handling. 5. Test quality, especially tests that mirror the implementation instead of proving behavior. 6. Maintainability smells: unnecessary abstraction, duplication, fragile coupling, or unclear naming. 7. Operational gaps: migration, observability, rollout, rollback, performance, and cost. 8. Required changes before approval. Return a verdict: accept, request changes, split the patch, or block.

Field guide takeaway: AI-generated code smells are not proof that the model failed, but they are proof that the work still needs review. Treat polished code as a draft until humans have checked the scope, verified the APIs, tested the edge cases, reviewed security boundaries, inspected dependencies, captured validation evidence, and accepted ownership for what the code will do after it leaves the prompt box.
