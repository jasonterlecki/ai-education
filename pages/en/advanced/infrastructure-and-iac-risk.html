Infrastructure and IaC Risk

Infrastructure-as-code is code with a crowbar. It can create access, delete networks, rotate certificates, expose storage, drain clusters, rewrite DNS, or spend money before anyone notices the smoke. Use AI here, but use it behind stronger fences than ordinary application work.

IaC is not just text

Terraform, Kubernetes manifests, IAM policies, DNS records, certificates, Helm values, deployment pipelines, and network rules describe living systems. A tiny edit can move real traffic, grant real authority, break real recovery paths, or quietly weaken a security boundary.

The question is not “Can the AI write the file?” The question is “What happens if this file is wrong and accepted?”
Privilege hides in small diffs A one-line IAM wildcard, security group rule, namespace binding, or service account annotation can change the effective access model.
Plans can look safe until context is missing A Terraform plan shows proposed changes, but not always the business reason, ownership model, compliance constraint, or downstream dependency.
Automation magnifies mistakes CI/CD systems can turn a flawed AI suggestion into a repeatable delivery path. The conveyor belt needs brakes, not enthusiasm confetti.

The danger zones

These areas deserve tighter prompts, smaller change sets, mandatory plans, explicit validation, and human review from someone who understands the blast radius.

TF

Terraform state and plans

State files, backend configuration, provider changes, imports, moves, destroys, and replacements can reshape the real environment. AI should explain the plan, not blindly bless it.

IAM

Identity and access

Roles, policies, bindings, trust relationships, service accounts, and workload identity decide who can do what. A broad permission can become a golden key with glitter on it.

K8s

Kubernetes clusters

RBAC, admission policy, namespaces, ingress, secrets, network policies, autoscaling, probes, and rollout settings can break production or widen access from inside the cluster.

DNS

DNS and traffic routing

Records, load balancers, ingress rules, CDN settings, health checks, and failover logic can redirect users, break certificates, or make recovery harder during an incident.

NET

Networking boundaries

VPCs, subnets, routing tables, firewalls, NAT, peering, private endpoints, and security groups define reachability. Reachability mistakes are wonderfully quiet until they are not.

TLS

Certificates and trust

Certificate renewals, CAs, DNS validation, secret mounts, and TLS termination can affect identity, encryption, and uptime. Expiry and misbinding deserve special suspicion.

CI

Deployment automation

Build scripts, runners, credentials, artifacts, approvals, environment promotion, and auto-apply workflows can turn a bad diff into a deployed bad diff at machine speed.

$

Cost and capacity

Instance sizes, autoscaling limits, storage classes, log retention, data transfer, and managed service settings can create surprise invoices or capacity cliffs.

The control ladder

Do not give AI the same authority at every step. Raise the control level as the work moves from analysis to production change.

Read-only analysis

Ask the AI to inspect files, summarize architecture, explain dependencies, identify owners, and list risks. No edits, no commands that change state.

Draft-only proposal

Ask for a PLAN.md, design note, migration sequence, or review checklist. Treat the result as a proposal, not an instruction to deploy.

Small scoped edit

Allow a narrow change with protected files, forbidden actions, validation commands, and a stop point. No opportunistic refactors.

Plan and review gate

Require generated plans, diffs, policy checks, test output, and a human explanation of blast radius before anything can merge or apply.

Controlled apply

Production applies need explicit approval, rollback notes, monitoring expectations, and a named human owner. The AI does not become the change authority.

Command boundaries

AI agents can read, format, lint, and explain. State-changing commands need fences. The difference between “show me” and “do it” is the drawbridge.

Usually safer inside a scoped agent run

These help the agent understand and validate without changing cloud state.

terraform fmt -check
terraform validate
terraform plan -out=tfplan
terraform show -no-color tfplan
kubectl diff -f ./manifests
kubectl kustomize ./overlays/dev
helm template ./chart
conftest test ./terraform
checkov -d .
tflint
Still require the correct workspace, backend, cluster context, credentials, and environment. “Safe command” does not mean “safe situation.”

Require explicit human approval

These can change, delete, expose, restart, or promote real infrastructure.

terraform apply
terraform destroy
terraform state rm / mv / import
kubectl apply / delete / patch / scale
helm upgrade --install
aws iam put-role-policy
aws route53 change-resource-record-sets
az role assignment create
gcloud projects add-iam-policy-binding
argocd app sync
pipeline deploy-to-prod
Do not let an AI agent run these just because it produced a plausible explanation. Plausible is not authorized; smooth prose is not change control.

Before AI changes infrastructure

Use this checklist before asking an AI agent to edit IaC, deployment configuration, access policy, routing, or cluster behavior.

Pre-flight checklist

1
State the environmentSpecify dev, test, staging, production, account, subscription, project, region, cluster, namespace, and workspace.
2
Fence the scopeName the files or modules that may be edited, the files that are protected, and the changes that are out of bounds.
3
Define the blast radiusAsk what can break: users, data, traffic, access, cost, observability, recovery, dependencies, and incident response.
4
Require plan outputFor Terraform, require plan review. For Kubernetes, require rendered manifests, diffs, and rollout impact notes.
5
Separate write from applyLet the AI draft the change. Keep apply, sync, promotion, and merge behind human review and approved automation.
6
Record assumptionsMake the agent list assumptions, unknowns, skipped validations, and places where it inferred behavior from incomplete context.

Review matrix

Use stricter review when a change crosses privilege, production, public routing, data, or automation boundaries.

Change type Minimum AI role Human review focus Validation evidence
Documentation or comments Draft and improve clarity. Accuracy, stale assumptions, wrong environment names. Rendered docs, links, and examples checked.
Terraform module edit Suggest bounded diff and explain plan. Resource replacement, state movement, provider behavior, variable defaults. fmt, validate, lint, plan, and reviewed plan summary.
Kubernetes manifest or Helm change Render, diff, and explain rollout risk. RBAC, secrets, probes, resources, ingress, network policy, disruption. template output, diff, policy checks, and rollout plan.
IAM or security boundary Analyze and propose least-privilege alternatives. Wildcards, trust policy, privilege escalation, cross-account access. Policy simulation or security review notes.
DNS, certificates, or traffic Map dependencies and rollback steps. TTL, validation records, failover, routing, monitoring, user impact. Diff, smoke test plan, rollback record, monitoring checks.
Deployment automation Review guardrails and propose safe gates. Secrets, permissions, environment promotion, approval bypass, auditability. Dry run, pipeline logs, permission review, approval evidence.

The practical rule

AI can help write, explain, compare, validate, and review infrastructure changes. It should not quietly become the actor that approves, applies, syncs, promotes, or owns the change.

For infrastructure, “done” means reviewed evidence, not a confident answer.

Reusable prompt

You are assisting with infrastructure-as-code.  Treat this as high-risk work.

Goal:
[Describe the change]

Environment:
[dev/test/staging/prod, account/project/subscription, region, cluster, namespace, Terraform workspace]

Allowed scope:
[Files, modules, manifests, or pipeline config you may inspect or edit]

Protected scope:
[Files, environments, resources, secrets, state operations, production applies, or commands you must not touch]

Required process:
1. Inspect the existing conventions before editing.
2. Identify blast radius: users, data, access, cost, traffic, rollback, monitoring, and dependencies.
3. Make the smallest safe change.
4. Do not run apply, destroy, sync, promote, delete, patch, or state-changing commands.
5. Run only approved validation commands.
6. Stop and report changed files, validation output, assumptions, risks, and what a human must review.
Field guide takeaway: Infrastructure work is where AI confidence can become operational gravity. Keep the agent useful, but boxed: read carefully, change narrowly, validate loudly, and leave approval to accountable humans with the keys, the pager, and the rollback map.
