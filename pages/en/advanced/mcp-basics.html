MCP Basics

Model Context Protocol is a standard way for AI applications to connect to external tools, data, and reusable workflows. It is not a magic permission slip. It is a plug shape, a handshake, and a boundary map for giving agents useful access without turning every integration into custom spaghetti.

M

The short version

MCP lets an AI host discover and use capabilities exposed by MCP servers. A server might expose a database schema as context, a ticket lookup as a tool, or a guided workflow as a prompt. The value is standardization: one clean protocol instead of one-off glue code for every tool, every model, and every application.

  • It gives agents a structured way to see available capabilities.
  • It separates the AI application from the external system implementation.
  • It makes integrations easier to reuse, review, and govern.
?

What problem does it solve?

Without a standard, every AI app needs a custom connector for every system. That creates duplicated code, inconsistent permissions, unclear auditing, and tool chaos wearing a tiny bow tie. MCP creates a common pattern for exposing context and actions to AI clients.

Before MCP Every integration is bespoke, brittle, and hard to explain to security.
With MCP Servers expose capabilities through a shared protocol that clients can discover and use.

The three moving parts

MCP is easiest to understand as a small cast of characters: the place where the user works, the connector inside that place, and the server that exposes useful capabilities.

H

MCP host

The host is the AI application the user interacts with: a chat app, coding assistant, IDE, desktop client, or agent environment. It decides what the user sees, what requests are allowed, and how model output is presented.

Client connection The host creates an MCP client for a server, negotiates capabilities, and passes structured requests and responses through the protocol.
S

MCP server

The server exposes capabilities from an external system. It might wrap GitHub, Google Drive, a database, a documentation store, a local filesystem, or a carefully fenced internal API.

Tools, resources, and prompts

These are the three primitives people usually trip over. They sound similar until you ask who controls them and whether they read, act, or guide.

T

Tools

Tools are callable actions. The model can request a tool call when it needs to query a system, run a calculation, open an issue, fetch a record, or perform some bounded operation.

Model-requested action
R

Resources

Resources are readable context. They expose information such as files, documents, database schemas, logs, or application state through stable identifiers instead of dumping everything into the prompt.

Application-controlled context
P

Prompts

Prompts are reusable interaction templates. They help users launch known workflows with the right structure, arguments, and context instead of making everyone reinvent the correct incantation.

User-invoked workflow

Choose the right primitive

The primitive choice is a governance decision in disguise. Pick wrong, and the model gets either too little context, too much authority, or a very shiny button connected to the wrong machinery.

Need Use Why Example
Read known information Resource The system provides context and the client decides when to include it. Expose a project README, API schema, log file, or policy document.
Perform a bounded action Tool The model can request an action with structured arguments and receive a structured result. Search tickets, create a branch, run a calculator, or query a database view.
Start a repeatable workflow Prompt The user can invoke a guided template with the right inputs and expectations. Generate a release note, run an incident summary, or start a code review checklist.
Control risky behavior Policy plus tool design MCP can expose capability, but it does not replace approval, authorization, logging, or human judgment. Require approval before writes, deployments, destructive changes, or messages to customers.

What MCP is not

A good mental model prevents architectural fog. MCP is plumbing, not prophecy. The water still needs valves.

!

Not automatic trust

An MCP server may be available, but that does not mean every exposed tool is safe for every user, model, repository, or environment.

!

Not a permission model by itself

You still need identity, authorization, scopes, secrets handling, approvals, logging, and review gates around real systems.

!

Not a context landfill

Resources should be curated. Throwing every document at the model creates noise, token waste, and confident confusion.

!

Not a substitute for validation

Tool results can be incomplete, stale, malformed, or misunderstood. Agents still need evidence checks before acting.

The practical deployment questions

Before adding an MCP server, ask operational questions first. The protocol tells systems how to speak. It does not tell the organization what the agent is allowed to say with a megaphone.

What data can the server see? List the files, APIs, databases, repositories, secrets, and metadata reachable through the server.
Which actions are read-only? Separate resources and safe lookups from write actions, destructive actions, and external communication.
Who approves risky calls? Define stop points for changes, sends, deploys, deletes, purchases, escalations, and permission changes.
What gets logged? Capture tool name, arguments, user, system target, timestamp, result summary, and approval evidence.
How is prompt injection handled? Treat external content as untrusted. Retrieved text can contain instructions designed to manipulate the agent.
How do you disable it quickly? Have an emergency off switch, revocation path, and rollback plan before the server becomes business-critical.
✓

A useful starter pattern

Start with read-only resources and harmless diagnostic tools. Add write actions later, one at a time, with explicit scopes, approval checkpoints, logging, and test cases. The boring path is the good path here. It is less fireworks, more drawbridge.

Field guide takeaway: MCP is not a magic tunnel that makes every system safe for AI. It is a structured way to expose tools, resources, and prompts, which means every connection still needs a clear purpose, narrow access, visible permissions, and human judgment before the model is allowed to touch real systems.
