Repository Instructions and Agents

AI coding agents work better when the repository carries its own map. Durable instructions explain where things live, which files are protected, how validation works, what security rules matter, and when the agent must stop instead of improvising a tiny cathedral in the wrong folder.

Why repository instructions matter

A prompt can tell an agent what you want today. Repository instructions tell it how the project works every day. They reduce repeated explanation, prevent stale assumptions, and give humans a stable place to encode architecture, conventions, safety rules, and review expectations.

The practical rule

If an AI agent can read, edit, run commands, or propose changes in a repository, the repository should contain durable guidance that tells it how to behave.

Do not rely on the agent remembering your standards. Put the standards where the agent has to read them.

The durable instruction stack

Good repo guidance is not one giant commandment scroll. It is a layered map: broad project context at the top, precise conventions near the code, and executable validation close to the work.

Layer 1

Purpose and boundaries

Explain what the repository does, what it must not do, which environments exist, and which areas are out of scope for agent edits.

Layer 2

Architecture map

Describe major folders, entry points, deployment paths, data stores, generated files, and the places where mistakes have sharp teeth.

Layer 3

Conventions and style

Record naming rules, formatting expectations, dependency patterns, branch habits, test conventions, and the preferred way to add new behavior.

Layer 4

Validation and stop points

List commands the agent may run, commands that require approval, review gates, report format, and conditions that force a pause.

What belongs in repo guidance

The goal is not to make the agent obedient by vibes alone. The goal is to give it enough grounded context that its edits become smaller, more reviewable, and less surprising.

Think of it as an onboard trail map

The agent should be able to open the repository, read the guidance, inspect the relevant files, and understand the safe path before it edits anything. Without that map, it may still move quickly, but fast movement through fog is not a delivery strategy.

README.mdHuman-facing project summary, setup notes, and basic entry points.
AGENTS.mdAgent-facing behavior rules, allowed scope, stop points, and validation expectations.
CODEX.mdOptional tool-specific or agent-specific guidance, especially for coding-agent workflows.
docs/maps/*.mdArchitecture maps, route maps, service maps, data-flow notes, and operational diagrams.
docs/runbooks/*.mdDeployment, rollback, migration, incident, and recovery procedures.

Include the details agents usually guess wrong

  • Which files are generated and should not be manually edited.
  • Which pages, modules, routes, environments, or Terraform workspaces are protected.
  • Where secrets are never allowed to appear, including logs, examples, screenshots, and tests.
  • How to run targeted checks instead of launching the entire project cannon.
  • What “done” means for this repository: tests, screenshots, diffs, approvals, and rollback notes.
  • Which conventions are local to this repo, even if a generic best practice says something else.

Guardrails that should be explicit

Agents do not need vague warnings. They need crisp borders. A good instruction file converts “be careful” into specific rules the agent and reviewer can both inspect.

Access rules

State what the agent may inspect, what it may edit, which branches or environments are off limits, and when it must ask before touching infrastructure, permissions, migrations, or production-adjacent code.

Security rules

Ban plaintext secrets, credential exposure, unsafe logging, broad permission grants, hidden trust changes, and placeholder examples that look like real tokens. Use fake values that cannot be mistaken for live ones.

Validation rules

Provide exact commands for linting, unit tests, type checks, formatting, static analysis, screenshots, smoke tests, and targeted checks. Also say which commands are too destructive or expensive to run without approval.

Change rules

Tell the agent to avoid unrelated refactors, preserve existing behavior unless instructed, prefer small diffs, explain any dependency changes, and leave migration or rollout steps in reviewable slices.

Communication rules

Require a final report with files changed, commands run, assumptions, risks, unresolved questions, and what a human should review before the next phase starts.

Version rules

Treat instruction files like product code. Update them when architecture changes, review them during PRs, and remove stale commands before they become little booby traps with markdown hats.

Good repository instructions

  • Short enough to be read, precise enough to guide behavior.
  • Organized by topic: scope, files, commands, security, validation, and stop points.
  • Grounded in the current repository, not generic advice from a motivational poster.
  • Written for both the agent and the human reviewer.
  • Updated when a command, workflow, folder, or environment changes.

Risky repository instructions

  • A thousand-line lore pile that the agent will skim, compress, or ignore.
  • Contradictory rules spread across multiple files with no precedence order.
  • Old commands that fail, target the wrong environment, or validate nothing useful.
  • Secret-shaped examples, real tokens, internal hostnames, or private account details.
  • “Use best practices” without saying what this repository actually requires.

Instruction file decision matrix

Use separate files when the audience or maintenance rhythm is different. Do not make one document carry every sandwich, wrench, and emergency flare in the repo.

Starter AGENTS.md template

Keep it specific. Replace bracketed text with the repository’s real boundaries, commands, and review expectations.

# AGENTS.md

## Repository Purpose
[Explain what this repository owns and what it does not own.]

## Required Working Pattern
- Inspect existing conventions before editing.
- Make the smallest complete change that satisfies the task.
- Do not perform unrelated refactors.
- Do not implement later phases unless explicitly instructed.
- Stop and report when scope, permissions, data, or security assumptions are unclear.

## Protected Areas
- Do not edit: [files, folders, generated assets, admin pages, production config].
- Do not run: [destructive commands, production commands, migration commands without approval].
- Do not expose: secrets, tokens, credentials, private URLs, customer data, or real identifiers.

## Project Map
- Main app: [path]
- Tests: [path]
- Configuration: [path]
- Generated files: [path]
- Documentation maps: [path]
- Runbooks: [path]

## Validation Commands
Use the smallest relevant validation set.
- Format: [command]
- Lint: [command]
- Unit tests: [command]
- Type check: [command]
- Smoke test: [command]

## Final Report Format
- Summary of change
- Files changed
- Commands run and results
- Assumptions made
- Risks or blockers
- Items requiring human review

Review the instruction file itself

Repository instructions can rot. When they rot, agents follow the smell. Review guidance with the same seriousness as any change that affects delivery behavior.

CurrentDo the commands, paths, owners, and environments still exist?
ConsistentDo README, AGENTS, runbooks, and workflow files agree?
SpecificDoes it name real boundaries instead of saying “be careful”?
SafeDoes it avoid secrets, real credentials, private data, and dangerous examples?
RunnableCan a contributor execute the validation commands as written?
ReviewableDoes it require a clear report after agent work?
BoundedDoes it keep agents from expanding the task without approval?
VersionedCan the team see when and why the guidance changed?

The maintenance loop

Instruction files are living guardrails. They should change when the repository changes, not six months later after an agent faceplants into a deprecated command.

Change the system

A folder, command, deployment path, permission model, tool, or validation step changes.

Update the map

Revise AGENTS, README, runbooks, or architecture maps in the same PR when possible.

Validate the guidance

Run the documented commands or confirm they still point to the right scripts and environments.

Review for conflict

Check for contradictions between repo files, CI workflows, local conventions, and tool-specific notes.

Record the version

Use the PR, changelog, or version header to show what changed and why future agents should care.

Field guide takeaway: Repository instructions are how a team turns repeated prompt reminders into durable operating knowledge. They do not replace human review, but they give agents a safer map, a shorter leash, and a brighter sign that says “stop here before you invent production folklore.”
