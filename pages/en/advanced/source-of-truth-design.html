Source of Truth Design

AI systems do not merely need more information. They need a way to know which information should win. Source of truth design is the discipline of deciding which systems, documents, timestamps, owners, and evidence are authoritative when the answer matters and the sources disagree.

Truth is a system property.

A chatbot can cite a document, but that does not mean the document is current, approved, complete, or allowed for the user. A retrieval system can find a similar paragraph, but that does not mean it found the governing answer. Source of truth design turns scattered knowledge into an order of authority the AI can respect.

The core rule: when sources conflict, the AI should not choose the most convenient text. It should follow a designed authority chain or stop and ask for human judgment.

What breaks without it

Old policy beats new policyThe model retrieves a stale PDF because it has better keywords than the approved current page.
Draft language becomes factA planning note, meeting transcript, or comment is treated as if it were approved doctrine.
Private context leaks into answersMaterial retrieved for one audience becomes visible to another because authority and permission were mixed together.

The four layers of source authority

A durable design separates where the answer lives, who owns it, how fresh it is, and whether the requester is allowed to use it.

1

System of record

The authoritative system where the truth is maintained: HR system, CRM, inventory database, policy portal, repository, ticket tracker, CMDB, data catalog, or approved knowledge base.

2

Owning role

The human or team accountable for the answer. A page without an owner is not a source of truth. It is a note with nice shoes.

3

Freshness rule

The timestamp, review cycle, lifecycle state, and deprecation rule that tell the AI whether a source is current, superseded, archived, or unknown.

4

Access boundary

The permission rule that determines who can retrieve, quote, summarize, export, or act on the source. Authority without access control becomes a velvet rope made of fog.

A source of truth decision flow

Use this flow before giving AI a pile of documents, connecting retrieval, or asking an assistant to answer questions from mixed systems.

Define the question class

Is this policy, customer data, operational status, architecture, pricing, legal wording, code behavior, or historical context?

Name the authoritative system

Identify the official home of that question class. If no official home exists, the system should report uncertainty.

Rank supporting sources

Decide which sources can support, clarify, or explain the answer without overriding the source of record.

Apply access and freshness

Check user permission, document status, review date, version, and deprecation markers before using the source.

Answer or escalate

If evidence is missing, stale, conflicting, or outside access boundaries, the AI should say so and route to an owner.

Conflict patterns to design for

Good retrieval is not enough. AI needs explicit behavior for the messy moments where sources disagree, overlap, expire, or speak with suspicious confidence.

!

Current source vs. familiar source

The older document may be quoted everywhere, but the current source should win. Familiarity is not authority, it is just repetition wearing a crown.

?

Ownerless source

If no team owns the content, the AI should treat it as background, not governing truth. Ownerless knowledge slowly becomes office folklore.

↕

Local exception vs. global rule

A team-specific runbook may override a general guide only within a defined scope. Local truth needs borders or it colonizes everything.

∅

Missing source

If the authoritative source is absent, inaccessible, or silent, the AI should not fabricate certainty from weaker evidence.

✓

Primary data vs. explanation

Dashboards, databases, and source code often outrank explanatory pages. Documentation explains truth; it does not always contain it.

⚑

Regulated interpretation

For legal, HR, finance, privacy, safety, and employment questions, the answer may require a named human authority rather than model synthesis.

Design patterns that keep truth governable

These patterns make it possible for people, retrieval systems, and agents to agree on which knowledge deserves the steering wheel.

Authority labels

Tag sources as authoritative, supporting, draft, archived, deprecated, historical, or personal notes. Retrieval should not flatten all of those into the same soup.

Owner and review metadata

Every high-value source should have an owner, last-reviewed date, next-review expectation, and escalation route. If the owner is gone, truth has a landlord problem.

Precedence rules

Write down which source wins by domain. For example: deployed configuration beats diagram, approved policy beats training slide, live ticket status beats old summary.

Answer provenance

Require answers to show which sources were used, which were ignored, and whether the answer came from authoritative records or weaker supporting context.

Artifacts that make source truth real

Source of truth design should leave tracks. If the rule exists only in someone’s memory, the AI will eventually trip over it with theatrical confidence.

1

Knowledge map

A table of question types, source systems, owners, access boundaries, freshness rules, and escalation contacts.

2

Source registry

A governed catalog of indexed sources, their lifecycle state, sensitivity, audience, and authority level.

3

Conflict policy

A practical rule set for what the AI should do when current, local, draft, archived, and conflicting sources appear together.

4

Deprecation markers

Visible metadata that tells humans and retrieval systems when a page is replaced, archived, or no longer authoritative.

5

Escalation paths

Named owners and channels for “the evidence conflicts,” “the answer is missing,” or “the AI should not decide this.”

6

Evaluation set

Known-answer tests that prove retrieval chooses the right source, handles stale documents, and refuses unsupported certainty.

Reusable source of truth design prompt

Use this before connecting AI to a knowledge base, repository, policy set, ticket system, or mixed document collection.

Help me design source-of-truth rules for this AI use case. Use case: [describe the assistant, agent, or retrieval workflow] Question types it must answer: [list policy, customer, technical, operational, strategic, HR, legal, finance, safety, etc.] Available sources: [list systems, repositories, documents, portals, tickets, databases, chats, dashboards, and owners] For each question type, define: 1. Authoritative source. 2. Supporting sources. 3. Sources that must never override the authoritative source. 4. Freshness and deprecation rules. 5. Access boundaries and sensitivity concerns. 6. Conflict behavior. 7. Escalation owner when evidence is missing or contradictory. 8. Evaluation cases that prove the AI follows the hierarchy. Return the result as a practical source-of-truth matrix and a short implementation checklist.

Field guide takeaway: Source of truth design tells AI which evidence is allowed to steer the answer. Do not let retrieval treat drafts, stale pages, meeting notes, old exports, and approved systems as equal citizens in the kingdom of facts. Define authoritative sources, owners, freshness rules, access boundaries, conflict behavior, and escalation paths so the model can say what it knows, what it does not know, and which human owns the truth when the sources disagree.
