Simple Project File Structure

A friendly map for where project files live, what each one does, and how AI tools can find the right instructions without digging through a hallway of mystery doors.

Why structure matters

A project folder is not just storage. It is the map that tells people, AI assistants, reviewers, and future-you where to look first. Good structure reduces repeated explanations, prevents important rules from being buried, and makes handoffs less like opening a drawer full of unlabeled cables.

The goal is not to create more files. The goal is to give every important file a clear job, a clear home, and a clear reader.

Think of it as a small office

1
The lobby signREADME.md tells everyone what the project is and where to start.
2
The house rulesAGENTS.md tells AI helpers what they may do, what they must avoid, and how to report work.
3
The recipe bookSKILLS.md and the skills folder hold repeatable ways to perform common work.

A simple starter structure

This layout works for many project types: a website, policy library, training package, report collection, internal playbook, or lightweight software project.

The files people ask about first

These are the common files that make a project understandable to humans and safer for AI-assisted work.

R

README.md

The project welcome mat. It explains what the project is, who it is for, where the important files live, and how someone should begin.

  • Put it at the root of the project.
  • Keep setup and navigation simple.
  • Link to deeper docs instead of copying everything.
A

AGENTS.md

The AI helper rulebook. It tells coding agents or AI assistants the project boundaries, allowed changes, review expectations, and stop conditions.

  • Put durable, project-wide AI rules here.
  • Use nested AGENTS.md files for folder-specific rules.
  • Say what AI must not do.
  • Require validation and a change summary.
S

SKILLS.md

The recipe index. It lists repeatable task patterns, such as adding a page, reviewing a document, preparing release notes, or checking links.

  • Put the skill catalog at the root.
  • Move detailed recipes into skills/.
  • Include inputs, outputs, checks, and stop points.
D

docs/

The knowledge cabinet. This folder holds explanations that help people understand the project without asking the same questions every week.

  • Use for background and reference material.
  • Keep decisions in docs/decisions/.
  • Keep glossary terms easy to find.
P

plans/

The change clipboard. This folder is for specific work that needs phases, review gates, validation, ownership, and rollback instructions.

  • Use PLAN.md for the active plan.
  • Use TESTPLAN.md for checks.
  • Use ROLLBACK.md before risky changes.
!

policies/

The guardrail drawer. This folder holds rules that should be hard to miss, especially around security, privacy, approvals, and sensitive information.

  • Use for SECURITY.md.
  • Use for data boundaries and approvals.
  • Make escalation rules explicit.

Minimum viable starter pack

For a small project, begin with four files. You can add nested folders later when the work becomes more complex.

1

README.md

What this project is, who owns it, what is current, and where someone should go next.

2

AGENTS.md

What AI assistants may do, what they may not do, how they should validate work, and when they must stop.

3

SKILLS.md

A short index of repeatable workflows. Start with two or three common tasks and expand only when needed.

4

docs/overview.md

A plain-language explanation of the project, major decisions, important terms, and links to supporting material.

Where should a new file go?

When in doubt, ask what job the file performs. The file’s job should decide its home.

?

Does it explain the whole project?

Put it in README.md or link from the README so people find it immediately.

AI

Does it instruct AI behavior?

Put durable project-wide rules in the root AGENTS.md. Put folder-specific rules in nested AGENTS.md files, such as docs/AGENTS.md or policies/AGENTS.md.

↻

Will the task repeat?

Put the method in skills/ so the team does not reinvent the same process every time.

✓

Is it for one change?

Put it in plans/. Include scope, non-goals, owners, validation, rollback, and approvals.

i

Is it background knowledge?

Put it in docs/. This includes explanations, glossary entries, decisions, and reference notes.

!

Can it affect safety or access?

Put it in policies/, and link it from AGENTS.md so AI helpers see the guardrail early.

▣

Is it an image, logo, or template?

Put it in assets/. Use clear subfolders such as images/, brand/, and templates/.

→

Is it generated work?

Put drafts, exports, reports, and temporary outputs in outputs/ so source files stay clean.

A beginner-friendly prompt for creating the structure

Use this when asking an AI assistant to help organize a new project. It keeps the request bounded, practical, and reviewable.

Before using the prompt, decide the project name, owner, audience, and risk level. The AI can draft the structure, but the team still owns the rules, approvals, and final decisions.

Ask for a proposed structure before files are created.
Keep AGENTS.md short and link to deeper files.
Require the assistant to explain why each folder exists.
Review safety, privacy, and approval files before using them.
Create a beginner-friendly project file structure for this project:

Project name: [name]
Audience: [who will use it]
Project type: [website, policy library, training package, report, app, other]
Risk level: [low, medium, high]

Include:
- README.md for project overview and navigation.
- AGENTS.md for project-wide AI assistant rules, boundaries, validation, and stop conditions.
- Nested AGENTS.md examples where folder-specific rules are useful, such as docs/AGENTS.md, plans/AGENTS.md, policies/AGENTS.md, and assets/AGENTS.md.
- SKILLS.md for repeatable task patterns.
- docs/ for explanations, glossary, and decisions.
- plans/ for implementation plans, tests, and rollback notes.
- prompts/ for reusable prompts.
- policies/ for security, privacy, approvals, and data boundaries.
- assets/ for images, brand files, and templates.
- outputs/ for drafts, reports, and generated artifacts.

For each file or folder, explain:
1. What belongs there.
2. What does not belong there.
3. Who should maintain it.
4. When it should be reviewed.

Do not create more folders than needed.  Keep the structure understandable to non-technical readers.

Common beginner mistakes

Do not turn AGENTS.md into a warehouse for every thought the project has ever had. Do not hide safety rules in random notes. Do not create fifteen folders just because the diagram looks impressive. A useful structure is boring in the best way: people can predict where things belong, AI helpers can find the right instructions, and reviewers can tell what changed.

Field guide takeaway: A project file structure is the project’s table of contents, front desk, safety rail, and lost-and-found bin. Put README.md at the entrance, root AGENTS.md where AI helpers can read the main rules, nested AGENTS.md files where specific folders need local instructions, SKILLS.md where repeatable work becomes reusable, and supporting folders where plans, docs, policies, assets, prompts, and outputs can live without turning the project into a drawer full of glitter and unlabeled keys.
