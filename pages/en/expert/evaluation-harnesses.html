Evaluation Harnesses

An evaluation harness turns “this answer looks fine” into repeatable evidence. It packages test cases, prompts, model settings, graders, thresholds, reports, and review gates so teams can tell whether an AI workflow improved, regressed, or merely learned to wear a nicer hat while making the same mistake.

Core Skill: Repeatable checks Use: Regression evidence Rule: Human review gates

What an evaluation harness is

A harness is a controlled way to run the same AI task against known examples and score the outputs. It does not make the model magically objective. It makes expectations visible, failures comparable, and changes harder to approve by charm alone.

An eval is not a trophy case. It is a smoke alarm, a regression net, and a measuring tape for behavior that would otherwise be judged by vibes.

Why teams need them

1
Models change

New models, prompts, tools, and retrieval settings can improve one behavior while breaking another.

2
Tasks drift

Support tickets, codebases, policies, customer language, and internal documents evolve over time.

3
Humans disagree

Rubrics reduce “I like it” debates by making quality criteria inspectable before the run.

The evaluation loop

A good harness is a loop, not a one-time science fair volcano. The team defines behavior, tests it, reads failures, adjusts the system, and keeps the cases that caught real problems.

Define the behavior

Name the task, audience, acceptable output, forbidden behavior, and quality bar.

Build the dataset

Collect normal cases, edge cases, adversarial cases, and known historical failures.

Choose graders

Use exact checks where possible, rubric scoring where needed, and human review for judgment-heavy work.

Run consistently

Pin prompts, model versions, tool settings, retrieval settings, and data versions where practical.

Analyze failures

Separate model failure, prompt failure, retrieval failure, tool failure, and ambiguous expectation.

Promote regressions

Turn serious failures into permanent test cases so the dragon does not respawn with a clipboard.

What belongs inside the harness

The useful harness is not just a spreadsheet of questions. It is the whole evaluation rig: inputs, expected behavior, scoring logic, run metadata, and decision thresholds.

D

Dataset

Representative examples, edge cases, negative cases, adversarial cases, and real incidents that should never come back wearing sunglasses.

P

Prompt and policy

The exact system, developer, and user instructions under test, including output format and any required safety constraints.

M

Model settings

Model name, version, temperature, tool availability, retrieval settings, context strategy, and any fallback behavior.

G

Graders

Exact-match checks, structured validators, rubric-based judges, pairwise comparisons, human review, or hybrid scoring.

T

Thresholds

Pass rates, severity limits, must-pass cases, regression tolerance, and when a change must be blocked.

R

Reports

Run summary, failures by category, examples that changed, approval status, and links to artifacts for review.

A

Audit trail

Who ran the harness, what changed, what version was tested, and which evidence supported the decision.

O

Owner

A named human or team responsible for updating cases, interpreting failures, and deciding when the harness is stale.

Different harnesses catch different creatures

One eval cannot prove everything. Use multiple lenses so a model that passes formatting does not quietly fail truthfulness, safety, retrieval, or business judgment.

✓

Format harness

Checks whether the output follows required structure: JSON schema, headings, table columns, markdown blocks, field names, or response length.

⌕

Retrieval harness

Tests whether the system finds the right source, cites the right passage, ignores stale material, and refuses when evidence is missing.

⚖

Rubric harness

Scores quality dimensions such as completeness, tone, risk coverage, clarity, correctness, and usefulness.

↔

Pairwise harness

Compares two outputs and asks which is better under a specific rubric. Useful when exact answers are impossible.

!

Safety harness

Uses hostile, sensitive, or risky cases to test refusal behavior, data handling, prompt injection resistance, and escalation.

↻

Regression harness

Locks in past failures and key success cases so prompt, model, or tool changes do not resurrect old goblins.

Match the grader to the question

Quality question Better grader Why Watch out for
Did it return valid JSON? Schema validator Deterministic checks are cheap, fast, and less subjective. Valid structure can still contain bad content.
Did it cite the right source? Source check Retrieval and citation failures need evidence-level verification. Similarity is not proof that the answer is supported.
Was the response useful? Rubric judge Usefulness often needs weighted criteria, not exact matching. Judge models need calibration and spot checks.
Which prompt is better? Pairwise comparison Side-by-side evaluation reduces some scoring ambiguity. Randomize order to avoid position bias.
Could this cause harm? Human review plus tests High-stakes failures need judgment, context, and accountability. Do not outsource approval to the system being evaluated.

Score what you will actually act on

Metrics are useful only when they drive decisions. A harness should say what gets promoted, blocked, investigated, rewritten, or escalated.

CorrectnessDoes the output answer the actual question without invented facts?
GroundingDoes it use the right evidence and avoid unsupported claims?
CompletenessDoes it cover the required decisions, risks, owners, and next actions?
UsabilityCan a human apply the output without decoding a fog sculpture?
SafetyDoes it avoid leaking data, unsafe tool use, hidden commitments, or overconfident advice?

Failure categories make results useful

A pass or fail number is not enough. Label failures so the team knows whether to fix the prompt, the dataset, the retrieval layer, the tool boundary, or the expectation.

F

Fact failure

The output is wrong, outdated, unsupported, or contradicted by the source material.

S

Scope failure

The model answers a broader, narrower, or adjacent task instead of the one actually assigned.

P

Policy failure

The output violates a safety rule, data boundary, approval gate, formatting requirement, or tone constraint.

R

Retrieval failure

The system uses the wrong source, misses the right source, cites irrelevant text, or trusts stale content.

T

Tool failure

The model chooses the wrong tool, calls it with unsafe arguments, ignores tool results, or treats a tool result as authority.

E

Expectation failure

The test case or rubric is ambiguous, unrealistic, or no longer matches the real workflow.

Artifacts that make evals operational

A harness becomes durable when it lives with the work: versioned datasets, documented rubrics, repeatable runners, and review notes that survive the meeting.

1

eval-dataset.jsonl

Case ID, input, expected properties, source references, tags, severity, and notes about why the case exists.

2

rubric.md

Scoring criteria, severity definitions, examples of pass and fail, and rules for when human judgment wins.

3

runner script

Repeatable command that executes the cases, captures outputs, and writes a report without hand-copy acrobatics.

4

report.md

Run metadata, pass rate, regressions, high-severity failures, examples, and recommended decision.

5

blocklist cases

Must-pass examples for safety, data handling, prompt injection, unsupported claims, and destructive tool use.

6

change log

Which prompt, model, retrieval, or tool settings changed, and which eval results justified the change.

Harness readiness checklist

  • Does each test case explain why it exists?
  • Are high-risk failures represented as must-pass cases?
  • Are prompts, model settings, tools, and retrieval settings captured?
  • Is the grading method appropriate for the quality question?
  • Are thresholds tied to a real decision?
  • Can humans inspect representative failures, not just the final score?
  • Is there an owner for updating stale cases?

Field guide takeaway: An evaluation harness is how teams stop asking whether an AI answer “seems good” and start collecting repeatable evidence. Build the harness around real examples, edge cases, failures, graders, thresholds, and human review gates so prompts, models, retrieval settings, and tools can change without quality sneaking out through the side door in a fake mustache.
