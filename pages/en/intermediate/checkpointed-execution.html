Checkpointed Execution

When an AI coding agent is working on a real system, do not ask it to eat the whole PLAN in one bite. Give it one phase, make it stop, review the diff, and only then release the next fox from the carrier.

Core Skill: One phase at a time Use: Stop, report, review Risk: Less drift, less blast radius

Big-bang build vs. checkpointed execution

Both approaches can produce code. Only one keeps assumptions, review, testing, and rollback from turning into soup.

Risky for real systems

Big-Bang Implementation

Ask the agent to implement the entire plan in one run and hope the architecture lands upright.

What usually happens

  • The agent starts making broad assumptions once the plan and codebase exceed easy context.
  • Later phases may be built on incorrect early guesses.
  • Unrelated files get touched because the agent tries to be helpful everywhere at once.
  • Testing is compressed into a short afterthought.

Why it feels efficient

  • It reduces prompting overhead.
  • It looks like forward motion.
  • It may work for small prototypes or disposable experiments.

Why it becomes expensive

  • Review is harder because the diff is large.
  • Rollback is harder because unrelated work is mixed together.
  • Corrections burn context because the agent must relearn what went wrong.
Best for delivery

Checkpointed Execution

Ask the agent to implement one bounded phase, validate it, summarize it, and stop.

What usually happens

  • The agent inspects only the relevant plan section and current code paths.
  • The diff stays small enough for human review.
  • Defects are caught before the next phase depends on them.
  • Each checkpoint becomes a clean handoff to the next run.

Why it is efficient

  • Less context is wasted on irrelevant future phases.
  • Corrections are local and easier to explain.
  • Validation becomes part of the rhythm, not a ceremonial gong at the end.

Why it is safer

  • Protected files can be re-stated at every phase boundary.
  • Scope creep is visible immediately.
  • Rollback maps cleanly to a phase, branch, or commit.

The checkpoint loop

Use this loop for AI coding agents, infrastructure changes, migrations, admin tools, and anything that can break real users.

Read the phase

Point the agent at only the relevant section of the plan and the files it must inspect.

Inspect first

Require it to understand existing conventions before editing. No architecture fan fiction.

Implement the slice

Make the smallest complete change that satisfies this phase and nothing beyond it.

Validate

Run linting, tests, syntax checks, screenshots, or smoke tests that match the touched files.

Stop and report

Summarize changed files, commands run, assumptions, risks, and blockers. Then wait.

Why checkpoints work

Checkpointing is not bureaucracy. It is a context-management strategy, a review strategy, and a safety strategy wearing the same hat.

1

Smaller blast radius

One phase means fewer files, fewer assumptions, and fewer places for an accidental change to hide.

2

Better human review

Reviewers can understand a focused diff. A giant diff turns review into archaeology with coffee.

3

Less context burn

The agent does not need to carry every future detail while solving the current problem.

4

Earlier corrections

If Phase 1 has the wrong assumption, you catch it before Phase 6 builds a decorative castle on top.

5

Cleaner rollback

Each checkpoint can become a commit, a branch review, or a restore point.

6

Stronger guardrails

Protected files, forbidden migrations, and validation commands can be repeated before every slice.

The practical rule

If the work touches production behavior, permissions, data, security, migrations, or user-facing workflows, use checkpointed execution.

Do not ask for “the whole thing.” Ask for “this phase, then stop.”

Reusable prompt

Implement PLAN.md Phase 1 only.

Before editing, inspect the existing conventions and the files relevant to this phase.

Do not implement later phases.
Do not perform unrelated refactors.
Do not touch protected files.
Preserve existing behavior unless this phase explicitly changes it.

When finished, stop and report:
- files changed
- validation commands run
- assumptions made
- risks or blockers
- what should be reviewed before the next phase

Fast decision matrix

Situation Use Why
Small throwaway prototype. One-shot implementation may be fine. The cost of being wrong is low and review burden is small.
Admin feature with permissions and public behavior. Checkpointed execution. Authorization, routing, and regression risk need phase boundaries.
Database schema plus application changes. Checkpointed execution. Schema assumptions should be verified before UI and runtime logic depend on them.
Large refactor across many files. Checkpointed execution. Small reviewable slices prevent accidental rewrites and review fatigue.
Design exploration or visual options. Vibe or prototype first. The goal is direction, not production-safe execution.
Legacy and new behavior must coexist. Checkpointed execution. Compatibility, migration, and rollback are the main work.
Committee takeaway: Checkpointed execution turns AI coding from a dramatic cannon launch into a controlled series of gates. It is slower than wishful thinking, faster than cleanup, and much kinder to anyone who has to review the diff.
