Where Should the Plan Live?

PLAN.md and an AI agent’s built-in plan mode can both organize the work. The difference is not just how much context they use. The difference is whether the plan becomes a durable project artifact or stays trapped inside one tool, one session, or one person’s workspace.

The simple idea

Use an agent’s plan mode to think through work in the current session. Use PLAN.md when the plan must be shared, reviewed, versioned, reused, audited, or handed off to another person or agent.

Agent plan mode is a thinking workspace. PLAN.md is a project artifact.

The practical rule

If the work has team impact, touches shared files, spans more than one session, or needs review before implementation, the plan should live in the repository.

Use plan mode to draft the map. Use PLAN.md when the map needs to survive the trip.

PLAN.md vs. agent plan mode

Both can consume context. Only one naturally becomes visible, reviewable, portable, and durable inside the project.

PLAN.md

Portable project memory

PLAN.md lives with the work. It can be committed, reviewed in a pull request, linked from a ticket, shared with teammates, reopened later, or used by a different AI tool.

  • Visible to the team, not just the current operator.
  • Works across agents, editors, vendors, and sessions.
  • Can be versioned, commented on, archived, or discarded.
  • Creates an audit trail for assumptions, phases, risks, and validation.
  • Reduces handoff loss when another person or agent continues the work.
Agent plan mode

Session planning tool

Agent plan mode is useful for reasoning through a task before execution. Depending on the tool, though, it may be difficult to share, export, review, preserve, or transfer.

  • Fast and convenient during the current interaction.
  • Good for small tasks, exploration, and immediate next steps.
  • May be tool-specific, hidden, ephemeral, or hard to cite.
  • May not appear in commits, tickets, pull requests, or documentation.
  • Can create split-brain planning if the repo says one thing and the agent thinks another.

Ask where the plan needs to live before deciding how formal it should be. The answer is usually about visibility, not verbosity.

Context cost vs. context return

Both planning approaches can consume similar context. The question is what the team gets back from that context after the current session ends.

Visibility

Who can see the plan?

If only the current user and agent can see it, the plan may be convenient but not collaborative. Shared work needs shared visibility.

Review

Can someone challenge it?

PLAN.md can be reviewed, commented on, diffed, and approved. A session plan may be harder to inspect before the agent acts.

Handoff

Can someone continue it?

A repo plan can be handed to another human or another agent without trying to reconstruct the session from memory crumbs.

Audit

Can the team explain intent later?

When something breaks, PLAN.md can show the intended phases, assumptions, validation, and rollback path.

Portability

Can another tool use it?

Agent plan mode may belong to one product. Markdown can be read by nearly every editor, repository platform, human, and AI tool.

Split-brain risk

Which plan wins?

If the agent has a hidden plan and the repo has a written plan, the written repo plan should be treated as the source of truth.

When agent plan mode is enough

Not every task needs a ceremonial scroll. Small work can stay lightweight when the blast radius is tiny.

Good use of agent plan mode

  • The task is small, local, and easy to inspect afterward.
  • The user wants the agent to think before editing.
  • The work is exploratory and may be thrown away.
  • No one else needs to approve the plan before action.
  • The output can be verified from the final diff or final answer.

When to promote to PLAN.md

  • The task crosses multiple files, systems, roles, or sessions.
  • The team needs to review or approve the approach.
  • The work touches production, infrastructure, data, permissions, policy, or public content.
  • A second person or AI agent may continue the work.
  • Rollback, validation evidence, or auditability matters.

Recommended workflow

Use the agent’s planning ability as a drafting engine, then promote the accepted plan into the repo when durability matters.

Ask for a draft plan

Let the agent propose phases, risks, assumptions, and validation. Do not let it implement yet.

Review the plan

Challenge scope, protected areas, missing context, non-goals, and approval requirements.

Save as PLAN.md

Once accepted, convert the useful plan into a repo artifact that teammates and future agents can read.

Execute by phase

Ask the agent to complete one bounded phase, report changes, and stop for review before continuing.

Update progress

Mark completed steps, capture validation evidence, and keep open questions visible.

Archive or discard

When done, archive the plan if history matters. Otherwise remove it and move durable lessons into AGENTS.md or docs.

Prompt pattern

This pattern tells the agent to plan first, then produce a durable repo-ready artifact instead of keeping the plan trapped in the session.

Reusable prompt

Use this when a task starts in agent plan mode but may need to become a shared implementation plan.

Before implementing anything, create a proposed plan for this work.

Task:
[Describe the work.]

First, reason through:
- scope and non-goals
- files or areas likely to change
- protected files, data, systems, or workflows
- risks and assumptions
- validation checks
- rollback or recovery needs
- questions that require human confirmation

Then output a repo-ready PLAN.md draft with:
1. Goal
2. Scope
3. Non-goals
4. Assumptions
5. Phased implementation steps
6. Validation per phase
7. Review checkpoints
8. Rollback or recovery notes
9. Open questions

Do not implement yet.  Stop after producing the plan.

Anti-patterns

These are the little trapdoors that make teams think they have a plan when they really have a puff of tool-specific smoke.

Hidden plan

The plan only exists inside the agent

Nobody else can review it, challenge it, or use it in a later session. Fine for small tasks. Fragile for team work.

Split brain

The repo plan and agent plan disagree

If there are two plans, the durable repo plan should win. Otherwise the agent may follow a private map through a public maze.

Context bonfire

The same plan is re-explained every session

If you keep spending tokens to restate the same plan, promote it into PLAN.md and let the repo carry the weight.

No review surface

The agent plans and acts in one motion

Planning is only useful if humans can inspect it before execution when the blast radius is meaningful.

Tool lock-in

The plan cannot leave the product

If the work may move between Codex, Cursor, Claude Code, Windsurf, Copilot, or a human editor, Markdown is the safer common language.

Ghost history

No one can explain why the change happened

If the plan vanishes after the session, the team may keep the result but lose the reasoning. That is how future debugging gets haunted.

Field guide takeaway: Use agent plan mode to think quickly inside the current session. Use PLAN.md when the plan must become project memory. If the work needs review, handoff, auditability, rollback, multi-session continuity, or team visibility, the plan belongs in the repo, not just inside the agent’s head.
