Review Gates and Rollback

A review gate is a decision point before a change reaches real users, systems, or data. Rollback is how you undo the change if it goes wrong. AI makes both matter more, because it produces polished work quickly and the polish can hide problems.

Core Skill: Approve changes with evidence and an undo plan Use: Before an AI-assisted change goes live Rule: Some actions need a gate before, not a rollback after

Why AI changes the review problem

AI output is fluent, fast, and plentiful. A reviewer faces a large diff and a confident explanation, and it is tempting to read the explanation and approve. That is the failure to avoid. Review the change, not the description of the change. The summary tells you what the AI believes it did. The diff shows what it did.

Useful review gates

You do not need all of them every time. Pick the ones that fit the risk.

Diff review

Read exactly what changed and why. Not the summary of the change.

Tests

Run automated checks that match the changed behavior.

Linting

Catch syntax, style, and formatting problems early.

Approvals

Name the people who must sign off, and what they are signing.

Feature flags

Separate deploying a change from exposing it to users.

Dry runs

Preview infrastructure, migration, or operational changes before applying them.

Rollback instructions

Write the recovery path before release, not after a failure.

Audit trail

Keep a record of changes, validation, and approvals. Do not store prompts that contain sensitive data.

Stopping conditions

Name the signals that pause or cancel the change.

What to look for in an AI-made diff

Unrequested changes

Files or behavior outside what you asked for. “While I was there” edits are a common sign the agent drifted.

Weakened or deleted tests

Removed assertions, skipped tests, or loosened checks that make a failure disappear.

New dependencies

Packages you did not ask for. Check they exist, are maintained, and are the ones you meant.

Hard-coded values and secrets

Keys, passwords, URLs, or sample data left in the code or config.

Changed permissions or config

Access, scopes, flags, or environment settings that widen what the change can reach.

For a longer list, see AI-Generated Code Smells and Code Review with AI.

“Tests pass” is a weak gate on its own

AI can write tests that pass without proving anything, or change a failing test until it passes. Check that the tests were not edited to fit the change, and where you can, confirm that a new test fails before the fix and passes after. A green result is evidence only if the tests were meaningful.

How strong should the gate be?

Can it be undone?

Rollback only helps with things that can be reversed. Sort the change first.

Easy to undo

  • A draft document with version history.
  • Code on a branch, or behind a feature flag.
  • A change you can revert with one command.

Hard or impossible to undo

  • An email or message that was sent.
  • Deleted data without a backup.
  • A payment, a public post, or a permission granted.

For the second group, put the gate before the action. A rollback plan cannot unsend a message. Add a preview, a confirmation, and a named approver instead.

Rollback basics

  1. Capture the previous state before the change: the commit, the version, a backup, or the old setting.
  2. Write the exact undo steps in plain language, where someone else can find them.
  3. Check that the undo itself is safe. Reverting a data change can be as risky as the change.
  4. Try the undo once when the stakes justify it.
  5. Decide who is allowed to call it, and what signal triggers it.

Stopping conditions that are specific

“Stop if something looks wrong” is not a condition. Write ones you can check:

  • The diff touches files outside the plan.
  • A test was edited, skipped, or removed.
  • The agent asks for broader permissions or access.
  • The output cites a source or package you cannot find.
  • Validation fails, or cannot be run.

Who reviews

For anything with real impact, the person who asked the AI to make the change should not be the only approver. A second person sees things the author stops noticing. An AI reviewer can add findings, but it is a helper, not a gate: a named human still approves. The Governed AI Delivery guide covers approver roles and decision records.

Gate or checkpoint?

The next page covers checkpointed execution. A checkpoint is a stop during the work, after one phase, so you can review before the agent continues. A gate is a decision before a change reaches users or systems. You usually want both.

A worked example

An agent updated a configuration file for the nightly report job.

Weak approval

  • “Looks good” on the agent’s summary.
  • No one opened the diff.
  • “Revert if something breaks.”

Strong approval

  • The diff shows two intended lines changed and nothing else.
  • The job ran in a test environment and the output matched.
  • The previous version is tagged, and the undo is one documented step.
  • A named person approved, and a stop condition is written down.

Try this before approving a change

  1. Review the diff, not just the summary.
  2. Run the agreed validation and check the tests were not changed to fit.
  3. Confirm who approves, and what they are approving.
  4. Decide whether it can be undone. If not, add a gate before the action.
  5. Write the undo steps and the stopping conditions.
  6. Keep the evidence in the ticket, commit, pull request, or release notes.

Prompt to draft a checklist

Review this proposed change and draft review gates and a rollback plan.

Change: [describe it, without secrets or sensitive data]
Where it runs: [test, staging, production]
Who is affected: [users, team, customers]

Return: gates to apply, what to check in the diff, whether the change can be undone, undo steps, stopping conditions, and open questions.  Mark anything you are unsure of.

Do not use this prompt to decide whether a change is safe. It drafts a checklist for a person to complete and approve.

When you need more

This page covers the habit. For risk-tiered gates, evidence bundles, decision records, monitoring plans, and rollback by type of work, read Governed AI Delivery in the Advanced guides.

Field guide takeaway: Review gates are not friction for its own sake. They make AI-assisted changes observable, reversible, and accountable. Review the change, size the gate to the risk, write the undo before you need it, and for anything that cannot be undone, put the gate before the action.
