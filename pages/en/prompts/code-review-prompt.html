Code Review Prompt

Use this prompt to widen code review coverage across correctness, edge cases, security, tests, maintainability, and rollback without letting AI pretend it owns approval. The assistant can inspect the orchard. A human still decides whether the gate opens.

The AI-assisted review loop

AI review is useful when it is directed, bounded, and evidence-seeking. It should catch more things, ask better questions, and organize risk, not replace the accountable reviewer or rubber-stamp a merge.

Frame the change

Provide the diff, ticket, intended behavior, affected files, and non-goals. The model should know what the change is supposed to do before judging it.

Inspect by lens

Ask for separate passes across correctness, edge cases, security, performance, tests, maintainability, and rollback. One giant opinion blob is review soup.

Separate evidence from suspicion

Require file references, reasoning, confidence, and verification steps. A concern without a check is a smoke puff, not a stop sign.

Prioritize review findings

Sort findings by impact and likelihood. Critical defects, missing tests, and safety risks should not compete with preference confetti.

Keep humans accountable

Use the AI output as review input. The human reviewer decides what is valid, what must change, and whether the code is ready to merge.

The practical rule

Use this prompt when AI can help review a pull request, patch, generated code, configuration change, infrastructure update, migration, or automation script. The goal is broader inspection and better questions, not delegated approval.

AI can widen the flashlight beam. It does not become the person holding the merge key.

Copy-ready prompt

Replace bracketed sections with the pull request, diff, files, commands, and project rules. Keep the approval boundary intact. That is the tiny lock on the code barn.

Review scaffold 
Role:
Act as a careful AI code review assistant.  Your job is to widen review coverage, identify risks, ask useful questions, and suggest verification steps.  You are not the approver.  Do not claim that the code is safe to merge.  A human reviewer remains accountable for approval.

Review target:
- Pull request, patch, commit, branch, or file set: [link, diff, pasted code, file list, or branch name]
- Intended goal of the change: [what the change is supposed to accomplish]
- Ticket, PLAN.md phase, specification, or acceptance criteria: [source of truth]
- Runtime or environment affected: [local, dev, staging, production, CI, infrastructure, admin, public UI, API, data pipeline]
- Risk level: [low / medium / high / unknown]

Context:
- Existing behavior that should be preserved: [known behavior]
- New behavior expected: [expected behavior]
- Non-goals: [what this change should not do]
- Relevant conventions: [style, patterns, architecture, framework, validation rules]
- Protected areas or sensitive concerns: [auth, secrets, IAM, DNS, database migrations, customer data, payment flows, production configs, compliance, accessibility, etc.]

Review boundaries:
- Do not rewrite the code unless asked.
- Do not approve the change.
- Do not invent requirements, owners, approvals, test results, security acceptance, or deployment status.
- Do not treat missing evidence as success.
- Do not assume silence from tests means safety.
- If you lack enough context to judge something, mark it as an open question or verification need.
- Separate confirmed issues from possible concerns and stylistic preferences.

Review method:
Perform separate review passes for each lens below.

1. Correctness and behavior
   - Does the change appear to implement the intended behavior?
   - Are there logic errors, wrong assumptions, incomplete branches, race conditions, state issues, or broken integrations?
   - Does it preserve existing behavior that should not change?

2. Edge cases and failure modes
   - What happens with empty input, nulls, missing fields, duplicates, invalid values, timeouts, retries, partial failures, large data, concurrent use, or unexpected state?
   - Are errors handled in a way users, operators, or callers can understand?

3. Security and privacy
   - Are secrets, tokens, credentials, customer data, logs, prompts, responses, or sensitive fields exposed?
   - Are authorization, authentication, input validation, output encoding, access boundaries, and least privilege respected?
   - Is there prompt injection, command injection, SQL injection, path traversal, SSRF, XSS, deserialization, dependency, or supply-chain risk?

4. Tests and validation
   - Are tests added or updated for the behavior changed?
   - Are important edge cases covered?
   - What validation commands should be run?
   - What evidence is missing before review can be trusted?

5. Maintainability and readability
   - Is the code understandable and consistent with local conventions?
   - Are names, structure, comments, dependencies, and abstractions appropriate?
   - Is there unnecessary complexity, unrelated refactoring, hidden coupling, or future maintenance burden?

6. Observability and operations
   - Are logs, metrics, alerts, traces, audit entries, and error messages sufficient for the risk level?
   - Could this fail silently?
   - Would operators know what happened and what to do next?

7. Rollback and deployment safety
   - Can the change be rolled back cleanly?
   - Does it require migration, feature flags, backward compatibility, staged rollout, config changes, or manual steps?
   - Are deployment assumptions documented?

8. Documentation and communication
   - Do docs, comments, runbooks, release notes, or user-facing messages need updates?
   - Are limitations, assumptions, and owner responsibilities clear?

Output format:
Return the review in the following structure.

A. Review summary
- One-paragraph summary of what the change appears to do.
- Overall risk level: low, medium, high, or unknown.
- Do not approve or reject.  State what requires human review.

B. High-priority findings
For each finding:
- Title
- Severity: critical / high / medium / low
- Confidence: high / medium / low
- Evidence: file, function, snippet, behavior, or reasoning
- Why it matters
- Suggested fix or verification step
- Whether this should block merge pending human review

C. Medium and low-priority findings
Use the same format, but keep style preferences separate from functional issues.

D. Missing evidence
- Tests not shown or not run
- Validation commands needed
- Environment or data assumptions
- Security or privacy review still needed
- Questions for the author

E. Edge cases to test
List concrete test cases, including inputs, expected results, and failure conditions.

F. Human review checklist
Create a short checklist the human reviewer should complete before approval.

G. Safe follow-up prompt
Provide a follow-up prompt I can give an AI assistant if I want help fixing only the confirmed issues, without starting unrelated refactors.

Task:
Review the provided code or diff using the rules above.

Review lenses to include

A good AI review prompt gives the model several flashlights, not one blurry lantern. Ask for distinct review passes so security issues do not get buried under naming comments.

Correctness Does the code actually do what the change claims? Look for wrong branches, missing conditions, state problems, broken integrations, and preserved-behavior regressions.
Edge cases Review nulls, empty input, duplicates, invalid data, large payloads, retry behavior, timeouts, concurrency, partial failure, and awkward “fox got into the wires” states.
Security and privacy Check secrets, authorization, data leakage, injection risks, logging, prompt exposure, dependency risk, and whether least privilege survived the enthusiasm.
Tests and validation Ask what tests exist, what tests are missing, which commands should run, and what manual checks are needed before confidence becomes more than decorative fog.
Maintainability Look at names, structure, conventions, comments, coupling, complexity, dependency changes, and whether future maintainers will need a lantern and a sandwich.
Rollback and operations Review feature flags, migrations, compatibility, logs, metrics, alerts, deployment steps, rollback path, and how failure will be noticed before users start yodeling.

Weak prompt

This prompt invites a shallow pass. It may produce nice-sounding reassurance while skipping the things that actually hurt.

Review this code and tell me if it looks good.
  • No source of truth for intended behavior.
  • No risk level, environment, or affected system.
  • No separate security, testing, or rollback lens.
  • No requirement to distinguish evidence from guesses.
  • No human approval boundary.
  • No checklist for what must be verified before merge.

Stronger prompt

This version gives the assistant a target, a boundary, review lenses, and an output format that helps a human reviewer decide what deserves attention.

Review this pull request as an AI code review assistant.  Do not approve it.  Help me widen coverage before human review.

Goal:
The PR adds webhook token validation and routes approved Bitbucket events to Teams channels.

Preserve:
- Existing health check behavior
- Existing admin console routing
- Current logging format unless a security issue requires masking

Risk areas:
- Secrets and tokens
- Request validation
- Logging leakage
- Error handling
- Teams routing behavior
- Tests and rollback

Review passes:
1. Correctness and behavior
2. Edge cases and malformed requests
3. Security and privacy
4. Tests and validation commands
5. Maintainability and local conventions
6. Rollback and operational visibility

For each issue, provide severity, confidence, evidence, why it matters, and a suggested fix or verification step.

Also provide:
- Missing evidence
- Edge cases to test
- Human review checklist
- Safe follow-up prompt for fixing confirmed issues only

Human approval boundaries

AI review can be fast, broad, and annoyingly good at spotting forgotten branches. It is still not accountable for production outcomes. Keep these boundaries visible.

AI finds candidates It can identify possible bugs, risks, missing tests, and confusing code. It cannot decide those findings are sufficient for approval.
Humans judge relevance Reviewers decide whether a finding is real, important, accepted, deferred, or intentionally out of scope.
Evidence beats confidence A confident AI answer without file references, test evidence, or reasoning should not be treated as review proof.
Silence is not safety If AI finds nothing, that means it found nothing. It does not mean the change is safe, complete, secure, or ready to merge.
Risk needs owners Security, privacy, migration, infrastructure, customer impact, and production risks must have human owners and explicit decisions.
Tests are not optional glitter When behavior changes, review should include test evidence or a clear reason why the test gap is accepted.
Rollback must be real For risky changes, reviewers should understand how to disable, revert, migrate back, or contain failure.
Approval stays human The merge decision belongs to the accountable reviewer, maintainer, owner, or approval process.

Review traps to avoid

These are common ways AI-assisted review becomes theater. The output may look polished, but the safety net has decorative holes.

Asking “is this good?” That invites vibes. Ask for review lenses, evidence, severity, confidence, missing tests, and human decision points.
Letting style drown risk Formatting, naming, and preference comments should not bury authorization bugs, data leaks, broken rollback, or missing tests.
Reviewing without intent The assistant needs the intended behavior and non-goals. Otherwise, it reviews what the code is, not whether it does the right thing.
Trusting unexplained confidence Require evidence and verification steps. Confident prose can still be a cardboard castle with nice windows.
Skipping the repo rules AI should review against local conventions, AGENTS.md, tests, build commands, protected files, and security rules, not generic internet habits.
Using review as implementation Review should identify issues. Fixing them should be a separate bounded task with scope, validation, and stop conditions.

Fast decision matrix

Use AI review where extra coverage helps, but scale the prompt to the risk. A tiny copy change does not need a submarine inspection. IAM, payment, data, and deployment changes do.

Situation Prompt intensity What to require
Small documentation or comment change. Light. Clarity, correctness, links, unsupported claims, and whether the docs match actual behavior.
Feature code touching user-visible behavior. Medium. Correctness, edge cases, tests, accessibility if applicable, error handling, and rollback notes.
Authentication, authorization, secrets, customer data, payments, or public workflows. High. Security and privacy lens, least privilege, logging leakage, abuse cases, test evidence, and explicit human security review.
Terraform, Kubernetes, IAM, DNS, certificates, networking, or deployment automation. High. Blast radius, plan output, permissions, rollback, drift risk, environment targeting, and approval gates.
AI-generated fix after an AI review. Checkpointed. Fix confirmed issues only, avoid unrelated refactors, run validation, report changed files, and stop.
Large refactor or migration. Phased. Review one phase at a time, compare against the plan, require tests and compatibility checks, and preserve rollback options.
Prompt library takeaway: Use AI code review to widen the inspection beam, not to outsource judgment. Ask for evidence, missing tests, risks, and human review questions. Treat “no issues found” as one signal, not a merge blessing carved into stone by a silicon owl.
