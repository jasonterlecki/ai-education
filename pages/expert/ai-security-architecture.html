AI Security Architecture

AI security architecture defines where identity is enforced, what the AI can reach, how tools are isolated, how sensitive data is protected, what gets logged, and how incidents are handled when the model, a connector, a user, or an automation path goes sideways.

Identity before access Sandboxed tools Observable by design

The security architecture map

Do not secure an AI system only at the chat box. Secure the whole path: human, model, connector, tool, data store, action, log, and escalation route.

1

Identity

Know who is asking, which role they hold, which business context applies, and whether the action requires stronger authentication or approval.

2

Authorization

Grant access by task, data class, tool, environment, and action type. The AI should not inherit a giant master key because a user has one.

3

Isolation

Run code, commands, retrieval, and file operations inside bounded sandboxes with explicit network, filesystem, credential, and time limits.

4

Inspection

Apply DLP, prompt-injection screening, output review, policy checks, and approval gates before sensitive data leaves or risky actions execute.

5

Accountability

Log prompts, sources, tool calls, decisions, approvals, outputs, and exceptions so incidents can be reconstructed instead of guessed.

Architecture principle

Design AI as an untrusted reasoning service wrapped by trusted controls. The model may suggest, transform, retrieve, or execute through tools, but identity, permission, validation, logging, and approval should live outside the model.

Do not rely on instruction text alone. Prompts are useful, but they are not a permission system, a DLP engine, or an audit trail.
Do not give broad ambient credentials. Use scoped tokens, delegated access, short lifetimes, environment separation, and action-specific permissions.
Do not hide automation. If AI can act, humans need visibility into what it attempted, what it changed, what failed, and who approved it.

Identity and least privilege

AI does not remove access-control design. It makes access-control design more important because the system can combine information, tools, and actions faster than a human can manually inspect.

ID

User-bound sessions

Tie every interaction to a real user, group, role, tenant, and environment. Shared AI accounts blur accountability and turn incident response into fog archaeology.

LP

Task-scoped permissions

Authorize the action being requested, not just the person. Reading a document, editing a repository, applying Terraform, and sending a customer email are different risk events.

TTL

Short-lived credentials

Prefer delegated, expiring, auditable credentials. Long-lived secrets inside prompts, repo files, browser sessions, or automation configs are security glitter: impossible to fully clean up.

ENV

Environment separation

Separate dev, staging, and production access. A model that can experiment in a sandbox should not automatically be able to mutate production.

2P

Human approval for high-risk action

Require explicit approval for destructive operations, public communication, sensitive data export, infrastructure changes, permission changes, and financial actions.

DENY

Default deny

If a use case, connector, data class, command, or destination has not been approved, the safe architecture answer is no until reviewed.

Connector and tool boundaries

Connectors are where AI stops being a text generator and starts touching the organization. Treat every connector as a controlled bridge with toll gates, cameras, and a very serious sign.

Read-only knowledge zone

Approved documents, policies, runbooks, tickets, and knowledge sources. Enforce source permissions and cite retrieval results so users can inspect the trail.

Workspace edit zone

Drafts, branches, temporary files, non-production documents, and reviewable changes. The AI may prepare work, but review and approval remain outside the model.

Controlled execution zone

Commands, CI jobs, tests, scans, previews, and non-production automation. Require allowlisted commands, captured output, timeouts, and no hidden side paths.

Privileged action zone

Production writes, IAM, DNS, payments, customer messages, deployments, and incident changes. Require approval gates, break-glass rules, rollback, and full audit logging.

Sandboxing and data protection

Good sandboxes make unsafe moves boringly unsuccessful. The model can be wrong, the prompt can be hostile, and the tool can still say, “Nope, not through this door.”

FS

Filesystem boundaries

Limit which paths the AI can read or write. Protect secrets, build artifacts, deployment files, user uploads, and unrelated repositories from accidental edits.

NET

Network boundaries

Restrict outbound calls, internal services, metadata endpoints, package downloads, and unknown destinations. AI tools should not improvise network reach.

DLP

DLP inspection

Detect secrets, customer data, personal data, regulated data, credentials, tokens, and suspicious bulk export before prompts, retrieval, outputs, or tool calls cross boundaries.

PI

Prompt injection resistance

Treat retrieved documents, web pages, emails, tickets, and logs as untrusted content. They can contain instructions meant to override policy or steal data.

Key pattern: separate instructions from evidence

Retrieved content should provide facts, source material, or context. It should not be allowed to redefine system rules, bypass access checks, request secrets, disable logging, or command tools. The architecture should label retrieved text as data, not authority.

Logs, monitoring, and auditability

AI systems need observability that explains both technical behavior and decision behavior. A useful log answers who asked, what the model saw, what it did, what was blocked, and who approved the final action.

LOG

Interaction logs

Capture user identity, task type, selected model, approved tool path, prompt metadata, retrieval sources, and policy decisions. Avoid storing sensitive payloads unnecessarily.

TOOL

Tool-call logs

Record commands, parameters, files touched, API endpoints, exit codes, changed resources, and generated artifacts. Tool calls are the footprints in the wet cement.

REV

Review logs

Track approvals, rejections, overrides, comments, exceptions, and final human decisions. Silence is not approval unless the workflow explicitly says so.

DET

Detection signals

Alert on unusual data volume, new connector use, repeated blocked actions, prompt-injection patterns, sensitive exports, privilege changes, and automation outside normal windows.

RET

Retention rules

Keep enough history for audit and investigation while minimizing sensitive data storage. Logs are security instruments, not secret hoarding dragons.

REP

Replayable evidence

For high-risk workflows, preserve the exact plan, diff, validation result, approval record, and deployed version so failures can be reproduced and explained.

Incident response for AI systems

Plan for AI-specific failures before they happen. The first hour of an incident should not be spent discovering whether anyone logged the tool calls.

1

Contain the capability

Disable the connector, revoke scoped tokens, pause automation, block the affected workflow, or force read-only mode. Contain action first, then investigate the full story.

2

Preserve the evidence

Keep prompts, outputs, retrieval sources, tool logs, diffs, deployment records, policy decisions, approvals, and timestamps. Do not let helpful cleanup erase the crime scene.

3

Classify the failure

Was it bad permissioning, prompt injection, hallucinated execution, stale retrieval, unsafe automation, user misuse, data leakage, or a missing approval gate?

4

Correct the control

Patch the architecture, not just the prompt. Update connector scope, DLP rules, test cases, evaluation sets, approval policy, logging, documentation, and training material.

Control matrix

Risk area Architecture control Review question
Identity and impersonation User-bound sessions, SSO, role mapping, step-up authentication, no shared AI operator accounts. Can we prove who initiated the request and which permissions were used?
Overbroad connector access Least-privilege scopes, per-tool allowlists, data-class restrictions, tenant separation, and environment separation. Could this connector read or change anything unrelated to the approved task?
Prompt injection Untrusted-content labeling, instruction hierarchy enforcement, output filtering, and refusal to follow retrieved instructions. What happens if a document tells the AI to reveal secrets or ignore policy?
Secret leakage DLP scanning, secret detection, redaction, blocked destinations, vault-based retrieval, and short-lived credentials. Can secrets appear in prompts, outputs, logs, branches, tickets, or external tools?
Unsafe execution Sandboxed commands, explicit allowlists, no production writes without approval, dry-run defaults, and captured outputs. Can the AI execute a destructive command without a human gate?
Audit gaps Tool-call logs, source citations, approval records, exception tracking, version history, and retention policy. Can we reconstruct the decision and action path after a failure?

Artifacts to maintain

Security architecture becomes durable when it is written down, reviewed, versioned, and tested. Otherwise it turns into hallway folklore with a dashboard.

MAP

AI access map

List approved tools, connectors, datasets, environments, roles, data classes, and action types. Show which combinations are allowed, denied, or approval-gated.

RUN

Incident runbook

Define who can disable connectors, revoke credentials, preserve logs, notify stakeholders, assess data exposure, and approve restoration.

EVAL

Security evaluation set

Maintain prompt-injection tests, leakage tests, permission-boundary tests, bad-output examples, and regression cases for every high-risk workflow.

POL

Use-case policy

Define allowed work, restricted work, approved tools, forbidden data, review requirements, escalation paths, and exception handling.

KEY

Credential handling design

Document where credentials live, how tokens are issued, how scopes are limited, how rotation works, and what happens during suspected exposure.

OBS

Observability standard

Specify required logs, redaction rules, audit fields, alert triggers, dashboard views, retention periods, and ownership for monitoring.

Reusable architecture review prompt

Review this AI workflow as a security architecture, not as a prompt-writing exercise.

Assess:
- user identity and role enforcement
- least-privilege connector access
- data classes involved
- tool and command execution boundaries
- sandboxing assumptions
- DLP and secret leakage controls
- prompt-injection exposure
- logging and auditability
- approval gates for high-risk actions
- rollback and incident response

Return:
1. Approved parts of the design
2. Missing controls
3. Highest-risk failure paths
4. Controls that must live outside the model
5. Required logs and evidence
6. Human approval points
7. Recommended test and red-team cases
Field guide takeaway: AI security architecture is not a sterner prompt taped to a rocket. It is the control system around the rocket: identity, boundaries, sandboxes, DLP, logging, approvals, and incident response working together before the engine lights.
