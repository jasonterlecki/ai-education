MCP Security and Permissions

Model Context Protocol can turn an AI assistant into a well-connected operator: files, tickets, databases, repositories, calendars, APIs, and automation all within reach. That reach is useful only when the permissions are explicit, scoped, observable, revocable, and boring enough that nobody needs to guess where the drawbridge is.

Permission design Tool boundaries Human approval gates
MCP is not a magic permission bubble.

MCP standardizes how an AI application connects to tools, resources, and prompts. It does not automatically make every connected system safe. Security lives in the surrounding architecture: identity, authorization, server design, tool schemas, consent prompts, sandboxing, logging, data classification, and the ability to shut a risky connection down quickly.

The basic security question is not “can the agent use this?”

The better question is “what exactly can happen if the model misunderstands, overreaches, follows hostile content, or calls the right tool with the wrong arguments?”

1

Reachable systems

Inventory every system the MCP server can touch: repositories, databases, files, ticket queues, cloud APIs, internal services, SaaS tenants, secrets stores, and external communication channels.

2

Available operations

Separate passive context from active capability. Reading a schema, posting a message, deleting a branch, rotating a key, and deploying a service are not the same species of animal.

3

Actor and identity

Decide whether calls run as the human user, a service account, an environment role, or a delegated token. Shared “AI bot” power can become a permission fog machine.

4

Evidence trail

Log the requesting user, client, tool, arguments, target, timestamp, result summary, approval status, and correlation IDs. If nobody can reconstruct it, nobody can govern it.

A practical permission ladder

Grant capability in layers. Start with low-blast-radius context, then add action only when validation, review, and revocation are already in place.

0

No connection

The assistant can reason from pasted text, uploaded files, or user-provided snippets, but cannot query live systems.

Threats that deserve names, not vibes

MCP expands the attack surface because the model can now bridge untrusted text, privileged tools, and live systems. Give the dragons labels before they learn the floor plan.

!

Indirect prompt injection

External content retrieved through MCP can contain instructions aimed at the model: ignore rules, exfiltrate context, call a tool, or manipulate a summary.

Treat retrieved text as data, not command authority. The server can provide context, but the agent’s operating rules should remain above it.

⚠

Tool poisoning

Tool names, descriptions, schemas, examples, or metadata can nudge the model toward unsafe behavior if they are compromised or written carelessly.

Review tool descriptions like executable policy. A charming description can smuggle a crowbar under the welcome mat.

↯

Confused deputy

The model may use a legitimate permission for the wrong party, purpose, tenant, environment, or ticket. The call is authorized, but the intent is wrong.

Bind actions to user identity, workspace, ticket, environment, and approval context instead of trusting a free-floating instruction.

$

Overbroad scopes

A server that can “manage cloud resources” or “write repository files” is a permission thundercloud unless every action is narrowed and validated.

Prefer many boring tools over one heroic super-tool. Heroic tools age into incident reports.

◌

Credential leakage

Tool results, logs, stack traces, prompts, files, or environment variables can expose tokens and secrets if filtering is not deliberate.

Redact at the server boundary and again at logging boundaries. Secrets should not need a trench coat and false mustache.

⌁

Unsafe local execution

Local MCP servers and command-backed tools can turn model output into shell arguments, file writes, or process execution.

Use allowlists, static command templates, sandboxes, read-only mounts, and argument validation. Never let natural language become a shell with a party hat.

Controls that make MCP survivable in grown-up environments

Security is not one giant “are you sure?” popup. It is a mesh of small controls that keep the model, the user, the server, and the target system inside their lanes.

InventoryTrack every MCP server, owner, version, transport, reachable system, and exposed capability.
Least privilegeUse narrow scopes, per-user access, environment boundaries, and short-lived tokens.
Schema validationReject unexpected arguments, broad selectors, dangerous paths, unknown tenants, and ambiguous targets.
Consent gatesAsk for approval on exact actions, not vague intentions. “Deploy this diff to prod” beats “continue.”
ObservabilityCapture tool calls, result summaries, policy decisions, approval records, and rollback evidence.
RevocationHave a kill switch for a server, a tool, a user, a token, or a single integration path.

MCP security review checklist

Use this before enabling a new server, adding a new tool, or moving from a personal experiment to shared team use.

What is the smallest useful scope?Prefer read-only, single workspace, single repository, single environment, or single data class before expanding.
Does the server authenticate the user?Do not rely on the model saying who the user is. Use real identity and authorization checks.
Are tool descriptions safe?Review names, descriptions, schemas, examples, and hidden defaults for unsafe instructions or ambiguity.
Can the model see secrets?Check files, logs, environment variables, command output, stack traces, and error messages.
Are write actions separated?Keep read tools separate from write tools so approval and logging can match the actual risk.
Are external inputs quarantined?Retrieved pages, issues, documents, emails, and comments should be treated as untrusted content.
What happens on failure?Define timeouts, retries, partial failure handling, rollback, and who gets notified.
Who owns the server?Assign a human owner for patching, access review, incident response, and retirement.

Field guide takeaway: MCP security is not a checkbox you staple onto a tool server after launch. It is the operating boundary around what the model can see, what it can call, who approved that access, how each action is logged, and where a human must stop the machine before convenience becomes blast radius.
