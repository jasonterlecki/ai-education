Odeurs de code généré par l’IA

L’IA peut produire du code utile très rapidement, mais elle produit aussi du code fluide, plausible, et parfois discrètement faux. L’odeur n’est pas « l’IA a touché à ceci ». L’odeur apparaît lorsque le résultat a l’air terminé avant d’avoir mérité la confiance par le contexte, les tests, la revue de sécurité, et l’appropriation humaine.

La première odeur de code est une réponse propre sans preuve.

Le code généré par l’IA devrait être revu comme la contribution rapide d’un développeur junior avec un formateur impeccable et un sourire étrangement sûr de lui. Il peut être correct, mais il a quand même besoin d’alignement avec le contexte, de tests, d’analyse des cas limites, de revue des dépendances, et de contrôles de sécurité.

✓

Le code IA n’est pas automatiquement mauvais

La posture utile n’est pas une mise en scène de suspicion. L’IA peut accélérer le code répétitif, les tests, la documentation, les refactorisations, les exemples, et l’exploration. Le travail du réviseur consiste à séparer l’accélération utile de la fragilité cachée.

!

Le code IA n’est pas automatiquement terminé

Une réponse qui compile peut quand même manquer des règles d’affaires, mal utiliser des bibliothèques, aplatir la gestion des erreurs, sauter l’autorisation, inventer des API, créer des valeurs par défaut non sécuritaires, ou réussir le chemin heureux tout en laissant un petit jardin de râteaux pour la production.

Révisez l’affirmation, pas la confiance.

La fluidité du modèle n’est pas une preuve. Une preuve, c’est un test qui passe, un diff vérifié, une API confirmée, un changement borné, un modèle de menace, un plan de migration, ou un réviseur humain capable d’expliquer pourquoi le résultat est assez sécuritaire.

Odeurs courantes du code généré par l’IA

Ces odeurs apparaissent parce que l’IA tend à optimiser pour un artefact plausible et complet. Les vrais systèmes exigent du contexte, des contraintes laides, de vieilles décisions, la réalité du déploiement, et les petits gobelins qui vivent derrière chaque cas limite.

Exactitude

Appels d’API inventés

Le code utilise des méthodes, des indicateurs, des champs, des comportements de SDK, ou des hooks de framework qui n’existent pas, qui existaient dans une autre version, ou qui appartiennent à une autre bibliothèque.

Geste de revue : vérifiez chaque appel inconnu contre la version installée de la dépendance, pas contre la mémoire, l’impression, ou un blogue de 2019.

Exactitude

Vision en tunnel du chemin heureux

Le code gère l’exemple propre, mais oublie les entrées vides, les doublons, les échecs partiels, la pagination, les reprises, les délais d’attente, les valeurs nulles, les permissions, la localisation, et la concurrence.

Geste de revue : demandez ce qui doit mal tourner avant que ce code devienne dangereux, bruyant, ou coûteux.

Maintenabilité

Réécriture trop large

Le modèle modifie la structure autour du changement, renomme des concepts, reformate des fichiers non liés, ou crée une nouvelle abstraction alors qu’une petite correction était demandée.

Geste de revue : comparez le diff avec la portée demandée. L’intelligence supplémentaire paie son loyer seulement lorsqu’elle réduit le risque futur.

Tests

Tests qui reflètent l’implémentation

Les tests reproduisent les mêmes hypothèses que le code généré, simulent le comportement risqué au point de le faire disparaître, ou vérifient que le code fait déjà ce qu’il fait.

Geste de revue : testez le comportement, les limites, et les modes d’échec. Un test qui admire seulement le code est une minuscule machine à applaudissements.

Sécurité

Glissement de confiance envers les entrées

Le code accepte une entrée d’utilisateur, de fichier, d’API, ou d’outil comme sécuritaire parce que l’exemple généré utilise des données amicales.

Geste de revue : inspectez la validation, l’encodage, l’échappement, la paramétrisation, l’autorisation, la gestion des chemins, et la journalisation.

Sécurité

Commodité en forme de secret

Le code inscrit des jetons d’exemple en dur, imprime des valeurs d’environnement, valide des identifiants fictifs, ou déplace des données sensibles dans les journaux et les messages d’exception.

Geste de revue : vérifiez le chargement de configuration, la caviardisation des secrets, la sortie des journaux, les fixtures, la documentation générée, et les exemples.

Architecture

Correctif local, effet global

Un petit changement modifie la mise en cache, les reprises, les requêtes de base de données, les permissions, les coûts, les formats de messages, ou les tâches d’arrière-plan loin du fichier modifié.

Geste de revue : identifiez les consommateurs, les appelants, les files d’attente, les schémas, les migrations, la séquence de déploiement, et le chemin de retour arrière.

Architecture

Brouillard d’abstraction générique

Le modèle crée des helpers, des factories, des providers, des adapters, des managers, et des interfaces avant que le système en ait besoin.

Geste de revue : gardez le code ennuyeux jusqu’à ce que la duplication et la variation prouvent que l’abstraction a un travail à faire.

Livraison

Aucune histoire opérationnelle

Le code fonctionne dans l’éditeur, mais ne dit rien sur le déploiement, les métriques, les feature flags, l’ordre de migration, le backfill des données, la surveillance, ou le retour arrière.

Geste de revue : exigez des notes opérationnelles lorsque le changement peut affecter le comportement en production, le coût, les données, ou les utilisateurs.

La boucle de revue du code IA

La revue n’est pas un seul regard fixe sur un diff. C’est une boucle qui va de l’intention à la preuve, parce que le problème du code IA n’est souvent pas la syntaxe. C’est l’adéquation non vérifiée.

Retrouver l’intention

Qu’est-ce que le code devait accomplir, et qu’est-ce qui était explicitement hors portée?

Inspecter le diff

Quels fichiers ont changé, quels fichiers n’auraient pas dû changer, et quel comportement caché a changé avec eux?

Mettre les hypothèses au défi

Quelles entrées, états, versions, permissions, et défaillances le code a-t-il supposés en silence?

Valider les preuves

Quels tests, linters, scanners, builds, contrôles manuels, ou traces prouvent que le changement est assez sécuritaire?

Décider de la barrière

Fusionner, demander des changements, découper le correctif, ajouter des tests, ou arrêter parce que l’exigence elle-même n’est pas claire.

Matrice odeur vers action

Ne vous contentez pas d’étiqueter une odeur. Acheminez-la vers la prochaine action de revue utile, sinon le constat devient une note autocollante décorative.

Signal Cause probable Action du réviseur Barrière
Grand diff pour une petite demande Le modèle a optimisé pour une solution d’apparence complète plutôt que pour un changement minimal et sûr. Demander un correctif borné, séparer les refactorisations, et préserver le formatage non lié. Diviser ou réduire
Nouvelle dépendance Le modèle a choisi la commodité plutôt que la discipline de chaîne d’approvisionnement. Revoir la licence, la maintenance, l’historique de vulnérabilités, les alternatives, et si les outils intégrés suffisent. Revue de sécurité
Aucun test modifié Le modèle a traité l’implémentation comme si elle équivalait à l’achèvement. Exiger des tests de comportement, des tests de régression, ou une explication de la couverture existante. Preuve requise
Permissions, auth, ou chemins de données touchés Le code généré a peut-être traversé une frontière de sécurité sans la nommer. Revoir l’autorisation, l’identité, les frontières de locataires, la journalisation, le caviardage, et les cas d’abus. Examen élevé
Code propre, exigence floue Le modèle a rempli l’ambiguïté avec un comportement plausible. Retourner aux critères d’acceptation avant de polir l’implémentation. Clarifier d’abord
Tests réussis seulement avec des mocks larges L’intégration risquée a été simulée au point de disparaître. Ajouter au moins un test d’intégration, de contrat, ou de frontière réaliste. Prouver le comportement

Artefacts de revue qui gardent le travail honnête

Les artefacts transforment « j’ai regardé » en preuve de revue. Ils aident aussi à repérer le moment où un agent a quitté la tâche et est revenu avec une abstraction étrangement brillante.

D

Résumé du diff

Listez les fichiers modifiés, le comportement visé, les changements qui semblent accidentels, et ce qui a été délibérément laissé intact.

T

Preuve de test

Capturez les commandes exécutées, la portée des tests, les échecs, les tests sautés, les contrôles manuels, et pourquoi la preuve correspond au risque.

S

Notes de sécurité

Consignez les frontières d’entrée, les contrôles d’auth, la gestion des secrets, les dépendances, l’encodage des sorties, et le risque d’exposition des données.

R

Note de retour arrière

Expliquez comment annuler, désactiver, feature-flaguer, annuler une migration, ou restaurer l’ancien comportement si le changement se comporte mal.

A

Registre des hypothèses

Nommez les hypothèses dont dépend le code généré : version, schéma, permissions, forme des données, trafic, coût, ou comportement opérationnel.

O

Approbation du propriétaire

Identifiez qui est responsable d’accepter le comportement, pas seulement qui a demandé au modèle de le générer.

Field guide takeaway: Les odeurs de code généré par l’IA ne prouvent pas que le modèle a échoué, mais elles prouvent que le travail a encore besoin d’une revue. Traitez le code poli comme un brouillon jusqu’à ce que des humains aient vérifié la portée, confirmé les API, testé les cas limites, revu les frontières de sécurité, inspecté les dépendances, capturé les preuves de validation, et accepté la responsabilité de ce que le code fera après avoir quitté la boîte de prompt.
