Flux de travail IA orientés tests

Avant qu’un agent de codage IA modifie du code, définissez à quoi ressemble le bon comportement, comment il sera prouvé, et ce qui ne doit pas bouger. Un flux de travail axé sur les tests donne une cible à l’agent au lieu d’un banc de brouillard avec un clavier.

Pourquoi l’approche orientée tests compte avec les agents IA

Un agent IA peut produire du code convaincant plus vite qu’un humain peut examiner ses suppositions. Les tests, exemples, fixtures, et critères d’acceptation transforment le travail de « ça semble plausible » en « nous avons des preuves ».

🎯

L’agent reçoit une cible

Sans comportement attendu, l’agent peut optimiser pour le style, la commodité, ou une architecture inventée. Une consigne test-first lui dit ce que la réussite signifie avant qu’il commence à déplacer les meubles.

🧪

La révision obtient des preuves

Un réviseur ne devrait pas avoir à deviner si le changement fonctionne. L’agent devrait montrer le test ajouté ou mis à jour, la commande exécutée, et le résultat exact.

🧭

La dérive devient visible

Lorsque l’implémentation s’éloigne du test, l’écart devient visible tôt. Le test est la balise du sentier; le diff, ce sont les traces de renard dans la neige.

La boucle orientée tests

Cette boucle fonctionne pour les agents de codage, les développeurs humains qui utilisent l’IA, les scripts d’infrastructure, les transformations de données, les changements d’API, le traitement de formulaires, et l’automatisation qui exige une livraison contrôlée.

Décrire le comportement

Énoncez le comportement visible par l’utilisateur ou le système en langage clair. Incluez les cas normaux, les cas limites, et ce qui doit rester inchangé.

Choisir la preuve

Décidez comment le comportement sera validé : test unitaire, test d’intégration, essai à blanc, comparaison de fixtures, vérification de capture d’écran, règle de lint, test de fumée, ou liste de vérification manuelle.

Ajouter ou mettre à jour les tests

Demandez à l’agent de créer le plus petit test utile qui capture le comportement visé. Le test devrait échouer ou être incomplet avant que l’implémentation soit changée.

Implémenter selon le test

Laissez l’agent changer seulement les fichiers nécessaires pour faire passer la preuve choisie. Aucun refactoring non lié. Aucun détour panoramique à travers tout le dépôt.

Exécuter, rapporter, arrêter

L’agent exécute la validation, rapporte les fichiers modifiés, les commandes, les hypothèses, les échecs, et les risques restants, puis s’arrête pour révision avant la prochaine tranche.

La règle pratique

Avant qu’un agent écrive du code d’implémentation, faites-lui expliquer ce qu’il va prouver et comment. La preuve peut être automatisée ou manuelle, mais elle doit être assez explicite pour qu’un réviseur puisse la contester.

Ne laissez jamais le premier « test » être un utilisateur surpris, un déploiement brisé, ou un journal de production qui hurle en minuscules.

Prompt réutilisable

Utilise un flux de travail axé sur les tests pour ce changement.

Objectif :
[Décris le comportement dont nous avons besoin.]

Contraintes :
- N’implémente pas de refactorings non liés.
- Préserve le comportement existant, sauf si l’objectif le change explicitement.
- Ne touche pas aux fichiers protégés.
- Garde le diff facile à réviser.

Avant l’implémentation :
1. Inspecte les chemins de code pertinents.
2. Identifie la stratégie de validation.
3. Ajoute ou mets à jour le plus petit test utile, fixture, test de fumée, ou liste de vérification manuelle.
4. Explique ce que la preuve couvre et ce qu’elle ne couvre pas.

Ensuite, implémente seulement ce qui est nécessaire pour satisfaire cette preuve.

Quand tu as terminé, arrête-toi et rapporte :
- fichiers modifiés
- tests ou vérifications ajoutés
- commandes de validation exécutées
- résultats
- hypothèses formulées
- risques ou éléments restants à réviser manuellement

Matrice de décision pour la validation

Type de changement Bonne première preuve À surveiller
Fonction pure, analyseur, formateur, calculateur, ou logique de règles. Tests unitaires avec des entrées représentatives, des valeurs limites, et des cas d’échec. L’IA peut tester seulement le cas heureux. Exigez des cas limites et des exemples clairement nommés.
Point de terminaison d’API, contrôleur, webhook, ou récepteur de formulaire. Tests de requête et de réponse, échecs de validation, vérifications de permissions, et charges utiles de fixtures. Confirmez que l’authentification, les entrées mal formées, l’idempotence, et les messages d’erreur sont couverts.
Migration de base de données ou changement de modèle de données. Essai à blanc de migration, test de rollback, assertions de schéma, test de données d’amorçage, et vérification de compatibilité. Ne laissez pas l’agent présumer que les données héritées sont propres, complètes, ou structurées comme le nouveau modèle.
Interface utilisateur ou flux de contenu. Comparaison de captures d’écran, vérification d’accessibilité, test de fumée des routes, et liste de vérification d’acceptation manuelle. Une réussite visuelle n’est pas une réussite fonctionnelle. Confirmez les formulaires, les liens, la mise en page mobile, et les états vides.
Infrastructure, CI/CD, permissions, ou automatisation. Sortie de plan, essai à blanc, vérification de politique, linting, et gate d’approbation avant toute étape d’application. Exigez des notes explicites sur le rayon d’impact, un chemin de rollback, et la confirmation de l’environnement ciblé.
Correction de bogue pour un comportement de production. Test de régression qui échoue avant la correction et réussit après. Assurez-vous que l’agent prouve le bogue original, pas seulement une décoration voisine qui ressemble à un bogue.

Liste de vérification avant d’accepter le diff

Un flux test-first ne retire pas la responsabilité humaine. Il donne aux réviseurs des outils plus tranchants, de meilleures preuves, et moins de créatures de brouillard cachées dans les coins.

Comportement nommé Le comportement attendu est écrit assez clairement pour qu’une personne autre que l’auteur puisse le réviser.
Preuve présente Il y a un test, une vérification, un essai à blanc, une capture d’écran, une fixture, ou une liste de vérification liée au comportement.
Périmètre resté clôturé L’agent n’a pas refactoré des fichiers non liés, renommé des concepts, ou « amélioré » l’architecture sans permission.
Échecs visibles Les écarts connus, les tests ignorés, les vérifications instables, et les besoins de vérification manuelle sont documentés.
Commandes répétables Les commandes de validation peuvent être relancées par un réviseur ou dans CI sans décoder le folklore de l’agent.
Comportement existant protégé Les chemins hérités, les frontières de permissions, les routes publiques, les formats de données, et les flux utilisateurs n’ont pas été brisés discrètement.
Cas limites inclus Les entrées vides, les entrées invalides, les permissions manquantes, les requêtes en double, et les valeurs limites ont été considérées.
Prochaine étape bornée L’agent s’est arrêté avec un résumé propre avant de glisser vers la phase suivante ou d’inventer du travail futur.
À retenir du guide de terrain : Le travail IA axé sur les tests transforme un agent de codage, de grand improvisateur confiant, en collaborateur borné. Définissez le comportement, choisissez la preuve, implémentez la plus petite tranche, exécutez les vérifications, et faites arrêter l’agent avant que le brouillard revienne.
