Hiérarchie Markdown pour les agents d’IA

Les agents d’IA ne traitent pas tous les fichiers d’un dépôt de la même manière. Certains fichiers Markdown servent de règles opérationnelles, certains servent de cartes de projet, et certains sont des preuves de soutien au bord du sentier.

L’idée simple

Un dépôt peut contenir de nombreux fichiers Markdown, mais un agent d’IA doit savoir lesquels sont des instructions, lesquels sont des explications, et lesquels ne sont que des notes de soutien.

Plus un fichier se trouve haut dans la hiérarchie, plus il devrait influencer le comportement de l’agent avant que celui-ci modifie, exécute des commandes, ou propose des changements.

Pourquoi les débutants devraient s’en soucier

Sans hiérarchie claire, un agent peut suivre des notes périmées, ignorer des règles de sécurité, mal comprendre le projet, ou traiter un fichier de tâche aléatoire comme plus autoritaire que les vraies règles opérationnelles de l’équipe.

Un bon ordre de contexte empêche l’agent de transformer le dépôt en canon à confettis avec accès aux commits.

La pyramide

Ce graphique montre une hiérarchie pratique. Il ne s’agit pas de déterminer quel fichier est « meilleur ». Il s’agit de comprendre quel fichier a habituellement plus d’autorité sur le comportement de l’agent.

Ce que fait chaque couche

Les noms de fichiers sont la partie importante. Les formulations plus élégantes peuvent venir ensuite. D’abord, rendez la carte lisible.

Règles les plus fortes

AGENTS.md

Utilisez ce fichier pour les règles de comportement des agents, les actions interdites, les exigences de validation, les limites d’approbation, et les instructions opérationnelles à l’échelle du dépôt.

Travail spécialisé

SKILLS.md

Utilisez ce fichier pour les procédures propres au projet, les flux de travail répétables, les modèles de commandes sécuritaires, les habitudes de révision, et les capacités spécialisées des agents.

Forme d’exécution

PLAN.md, SPEC.md, RUNBOOK.md

Utilisez ces fichiers pour définir l’intention, les exigences, les étapes de déploiement, les procédures opérationnelles, les critères d’acceptation, et les attentes de reprise.

Vérité du projet

README.md, CONTRIBUTING.md

Utilisez ces fichiers pour l’objectif du projet, la configuration, la vue d’ensemble de l’architecture, le développement local, les règles de contribution, et l’accueil convivial pour les humains.

Portée de tâche

ISSUE.md, TASK.md, PROMPT.md

Utilisez ces fichiers pour les éléments de travail précis, les changements demandés, les contraintes de prompt, et le contexte actuel de livraison.

Détails de soutien

CHANGELOG.md, docs/*.md, notes/*.md, logs/*.md

Utilisez ces fichiers pour l’historique des versions, les changements connus, le matériel de contexte, les notes de réunion, les preuves, l’historique de conception, les dossiers de dépannage, et le contexte de priorité plus faible.

Bon usage et usage risqué

Le but n’est pas de créer de l’encombrement Markdown. Le but est de mettre les bonnes instructions au bon endroit.

Bon usage

Placez les règles générales pour agents près de la racine du dépôt, gardez les procédures spécialisées dans des fichiers prévisibles, et utilisez les documents de tâche pour réduire la portée plutôt que pour contourner les règles de sécurité.

Usage risqué

Enterrer les instructions critiques dans des dossiers aléatoires, disperser des règles contradictoires dans plusieurs fichiers, ou supposer que l’agent découvrira chaque note avant d’agir.

Conclusion du guide de terrain : La hiérarchie Markdown est la pile d’instructions du dépôt. AGENTS.md établit les limites opérationnelles de l’agent, SKILLS.md enseigne les procédures répétables, les fichiers de planification structurent l’exécution, les fichiers README expliquent le terrain, et les notes de niveau inférieur fournissent des preuves sans prendre le commandement de l’expédition.
