Où le plan devrait-il vivre?

PLAN.md et le mode plan intégré d’un agent IA peuvent tous les deux organiser le travail. La différence n’est pas seulement la quantité de contexte utilisée. La différence est de savoir si le plan devient un artefact de projet durable ou s’il reste emprisonné dans un outil, une session, ou l’espace de travail d’une seule personne.

L’idée simple

Utilisez le mode plan d’un agent pour réfléchir au travail dans la session courante. Utilisez PLAN.md lorsque le plan doit être partagé, révisé, versionné, réutilisé, audité, ou transféré à une autre personne ou à un autre agent.

Le mode plan de l’agent est un espace de réflexion. PLAN.md est un artefact de projet.

La règle pratique

Si le travail a un impact d’équipe, touche des fichiers partagés, s’étend sur plus d’une session, ou exige une révision avant la mise en œuvre, le plan devrait vivre dans le dépôt.

Utilisez le mode plan pour rédiger la carte. Utilisez PLAN.md quand la carte doit survivre au voyage.

PLAN.md ou mode plan de l’agent

Les deux peuvent consommer du contexte. Un seul devient naturellement visible, révisable, portable, et durable dans le projet.

PLAN.md

Mémoire de projet portable

PLAN.md vit avec le travail. Il peut être commité, révisé dans une pull request, lié depuis un ticket, partagé avec les coéquipiers, rouvert plus tard, ou utilisé par un autre outil d’IA.

  • Visible pour l’équipe, pas seulement pour l’opérateur courant.
  • Fonctionne entre agents, éditeurs, fournisseurs, et sessions.
  • Peut être versionné, commenté, archivé, ou supprimé.
  • Crée une piste d’audit pour les hypothèses, phases, risques, et validations.
  • Réduit la perte de transfert quand une autre personne ou un autre agent continue le travail.
Mode plan de l’agent

Outil de planification de session

Le mode plan de l’agent est utile pour raisonner sur une tâche avant l’exécution. Selon l’outil, toutefois, il peut être difficile à partager, exporter, réviser, préserver, ou transférer.

  • Rapide et pratique pendant l’interaction courante.
  • Bon pour les petites tâches, l’exploration, et les prochaines étapes immédiates.
  • Peut être propre à un outil, caché, éphémère, ou difficile à citer.
  • Peut ne pas apparaître dans les commits, tickets, pull requests, ou la documentation.
  • Peut créer une planification à cerveau divisé si le dépôt dit une chose et l’agent en pense une autre.

Tableau de décision

Demandez où le plan doit vivre avant de décider à quel point il devrait être formel. La réponse concerne généralement la visibilité, pas la verbosité.

Coût du contexte et rendement du contexte

Les deux approches de planification peuvent consommer un contexte semblable. La question est ce que l’équipe récupère de ce contexte après la fin de la session courante.

Visibilité

Qui peut voir le plan?

Si seuls l’utilisateur courant et l’agent peuvent le voir, le plan peut être pratique, mais pas collaboratif. Le travail partagé exige une visibilité partagée.

Révision

Quelqu’un peut-il le contester?

PLAN.md peut être révisé, commenté, comparé en diff, et approuvé. Un plan de session peut être plus difficile à inspecter avant que l’agent agisse.

Transfert

Quelqu’un peut-il continuer?

Un plan dans le dépôt peut être remis à un autre humain ou à un autre agent sans reconstruire la session à partir de miettes de mémoire.

Audit

L’équipe peut-elle expliquer l’intention plus tard?

Quand quelque chose casse, PLAN.md peut montrer les phases prévues, hypothèses, validations, et le chemin de retour arrière.

Portabilité

Un autre outil peut-il l’utiliser?

Le mode plan de l’agent peut appartenir à un seul produit. Markdown peut être lu par presque tous les éditeurs, plateformes de dépôt, humains, et outils d’IA.

Risque de cerveau divisé

Quel plan gagne?

Si l’agent a un plan caché et que le dépôt a un plan écrit, le plan écrit du dépôt devrait être traité comme source de vérité.

Quand le mode plan de l’agent suffit

Toutes les tâches n’ont pas besoin d’un parchemin cérémoniel. Le petit travail peut rester léger quand le rayon d’impact est minuscule.

Bon usage du mode plan de l’agent

  • La tâche est petite, locale, et facile à inspecter ensuite.
  • L’utilisateur veut que l’agent réfléchisse avant de modifier.
  • Le travail est exploratoire et peut être jeté.
  • Personne d’autre n’a besoin d’approuver le plan avant l’action.
  • La sortie peut être vérifiée à partir du diff final ou de la réponse finale.

Quand promouvoir vers PLAN.md

  • La tâche traverse plusieurs fichiers, systèmes, rôles, ou sessions.
  • L’équipe doit réviser ou approuver l’approche.
  • Le travail touche la production, l’infrastructure, les données, les permissions, les politiques, ou le contenu public.
  • Une deuxième personne ou un deuxième agent IA peut continuer le travail.
  • Le retour arrière, les preuves de validation, ou l’auditabilité comptent.

Flux de travail recommandé

Utilisez la capacité de planification de l’agent comme moteur de brouillon, puis promouvez le plan accepté dans le dépôt quand la durabilité compte.

Demander un brouillon de plan

Laissez l’agent proposer phases, risques, hypothèses, et validation. Ne le laissez pas encore mettre en œuvre.

Réviser le plan

Contestez la portée, les zones protégées, le contexte manquant, les non-objectifs, et les exigences d’approbation.

Enregistrer comme PLAN.md

Une fois accepté, convertissez le plan utile en artefact de dépôt que les coéquipiers et futurs agents peuvent lire.

Exécuter par phase

Demandez à l’agent de compléter une phase bornée, de rapporter les changements, et de s’arrêter pour révision avant de continuer.

Mettre à jour le progrès

Marquez les étapes terminées, capturez les preuves de validation, et gardez les questions ouvertes visibles.

Archiver ou supprimer

Une fois terminé, archivez le plan si l’historique compte. Sinon, retirez-le et déplacez les leçons durables dans AGENTS.md ou les docs.

Modèle de prompt

Ce modèle dit à l’agent de planifier d’abord, puis de produire un artefact durable prêt pour le dépôt au lieu de garder le plan prisonnier de la session.

Prompt réutilisable

Utilisez ceci quand une tâche commence en mode plan de l’agent, mais pourrait devoir devenir un plan de mise en œuvre partagé.

Avant de mettre quoi que ce soit en œuvre, crée un plan proposé pour ce travail.

Tâche :
[Décrire le travail.]

D’abord, raisonne sur :
- la portée et les non-objectifs
- les fichiers ou zones susceptibles de changer
- les fichiers, données, systèmes, ou flux de travail protégés
- les risques et hypothèses
- les vérifications de validation
- les besoins de retour arrière ou de récupération
- les questions qui exigent une confirmation humaine

Ensuite, produis un brouillon PLAN.md prêt pour le dépôt avec :
1. But
2. Portée
3. Non-objectifs
4. Hypothèses
5. Étapes de mise en œuvre par phases
6. Validation par phase
7. Points de contrôle de révision
8. Notes de retour arrière ou de récupération
9. Questions ouvertes

Ne mets rien en œuvre pour l’instant.  Arrête-toi après avoir produit le plan.

Anti-modèles

Ce sont les petites trappes qui font croire aux équipes qu’elles ont un plan alors qu’elles ont vraiment une bouffée de fumée propre à un outil.

Plan caché

Le plan existe seulement dans l’agent

Personne d’autre ne peut le réviser, le contester, ou l’utiliser dans une session ultérieure. Correct pour les petites tâches. Fragile pour le travail d’équipe.

Cerveau divisé

Le plan du dépôt et le plan de l’agent ne concordent pas

S’il y a deux plans, le plan durable du dépôt devrait gagner. Sinon, l’agent peut suivre une carte privée dans un labyrinthe public.

Feu de joie de contexte

Le même plan est réexpliqué à chaque session

Si vous dépensez sans cesse des tokens pour redire le même plan, promouvez-le dans PLAN.md et laissez le dépôt porter le poids.

Aucune surface de révision

L’agent planifie et agit d’un seul mouvement

La planification est utile seulement si les humains peuvent l’inspecter avant l’exécution quand le rayon d’impact est significatif.

Verrouillage d’outil

Le plan ne peut pas quitter le produit

Si le travail peut passer entre Codex, Cursor, Claude Code, Windsurf, Copilot, ou un éditeur humain, Markdown est le langage commun plus sûr.

Histoire fantôme

Personne ne peut expliquer pourquoi le changement est arrivé

Si le plan disparaît après la session, l’équipe peut garder le résultat, mais perdre le raisonnement. C’est ainsi que le dépannage futur devient hanté.

Conclusion du guide de terrain : Utilisez le mode plan de l’agent pour réfléchir rapidement dans la session courante. Utilisez PLAN.md lorsque le plan doit devenir mémoire de projet. Si le travail exige révision, transfert, auditabilité, retour arrière, continuité multi-session, ou visibilité d’équipe, le plan appartient dans le dépôt, pas seulement dans la tête de l’agent.
