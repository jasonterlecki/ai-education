PLAN.md vs SPEC.md vs RUNBOOK.md

These three files are often treated like interchangeable project paperwork. They are not. A SPEC defines the target, a PLAN explains how the change will be built, and a RUNBOOK tells people how to operate, verify, recover, or repeat the result. When they are mixed together, AI assistants start steering from foggy coordinates.

Define the thing Plan the work Operate the result Reduce handoff drift

The three documents have different jobs.

Each file answers a different question. Keeping those questions separate makes the work easier to review, safer to delegate to an AI assistant, and less likely to collapse into a puddle of good intentions.

S

SPEC.md

The target contract. A SPEC describes what must be true when the work is finished. It cares about behavior, constraints, interfaces, data rules, user outcomes, non-goals, and acceptance criteria.

  • Defines scope, requirements, and boundaries.
  • Names what success looks like before anyone starts building.
  • Separates required behavior from optional implementation detail.
What are we making? What must be true? What is out?
P

PLAN.md

The execution route. A PLAN turns the target into a practical sequence of work. It names phases, files, dependencies, validation points, rollback thinking, and stop conditions.

  • Breaks the change into safe, reviewable steps.
  • Explains sequencing, risks, and checkpoints.
  • Gives an AI assistant a track to run on instead of a field to wander through.
How do we build it? What changes first? Where do we stop?
R

RUNBOOK.md

The operating manual. A RUNBOOK explains how to use, verify, troubleshoot, repeat, or recover the system once it exists. It is written for action under real conditions.

  • Captures commands, checks, owners, dashboards, and recovery steps.
  • Explains normal operation and abnormal recovery.
  • Turns tribal knowledge into repeatable procedure.
How do we run it? How do we know it worked? How do we recover?

A healthy handoff has a sequence.

The files can be created in different orders, but the cleanest delivery path usually moves from target to execution to operation. The paper trail becomes a tiny railway yard instead of a box of cables.

Intent

Describe the problem, audience, pain, desired outcome, and constraints. This may begin as a brief, ticket, meeting note, or stakeholder ask.

SPEC.md

Lock the target. Define behavior, acceptance criteria, data rules, edge cases, non-goals, and the review standard for done.

PLAN.md

Convert the target into phases. Include files to inspect, likely changes, validation commands, risk gates, and where the assistant must stop.

Implementation

Execute in bounded slices. Compare each slice against the SPEC and PLAN instead of trusting momentum, vibes, or a confidently glowing progress summary.

RUNBOOK.md

Preserve the operating knowledge. Explain setup, routine checks, verification, rollback, troubleshooting, escalation, and maintenance notes.

Common failure pattern: one file tries to wear three hats.

The fastest way to confuse an AI assistant is to bury requirements, implementation guesses, live commands, and recovery instructions in the same document without labels.

Mixed document smell

“The feature should let admins publish pages. Maybe use a database table. Run this command in production. If it fails, restore the old PHP file. Acceptance is whatever looks right.”

Separated document signal

SPEC states the publishing behavior. PLAN says how the migration will be implemented and validated. RUNBOOK explains how admins operate it and how production is recovered if the release goes sideways.

Which file should you ask the AI to create?

Pick the artifact based on the uncertainty in front of you. A vague goal needs definition. A defined goal needs sequencing. A live process needs operating instructions.

Use SPEC.md when

The target is fuzzy.

You need requirements, edge cases, user flows, constraints, non-goals, acceptance criteria, and clear review language before implementation starts.

Use PLAN.md when

The target is known.

You already understand what must be built, but you need phases, file targets, validation, rollback thinking, risk review, and checkpointed execution.

Use RUNBOOK.md when

The thing must be operated.

You need repeatable steps for deploys, imports, incident checks, admin tasks, support triage, scheduled work, or recovery under pressure.

Use all three when

The blast radius matters.

Anything involving production systems, user data, security controls, migrations, permissions, cost exposure, or cross-team ownership deserves the full stack.

Minimum useful contents.

A good document does not need to become a marble monument. It needs enough structure that a person or AI assistant can act without inventing the missing half of the map.

S

SPEC.md skeleton

  • Problem and audience
  • Goals and non-goals
  • User or system behavior
  • Inputs, outputs, and data boundaries
  • Edge cases and failure modes
  • Acceptance criteria
P

PLAN.md skeleton

  • Assumptions and prerequisites
  • Implementation phases
  • Files or areas to inspect
  • Validation commands and evidence
  • Risks, rollback, and stop points
  • Human approval gates
R

RUNBOOK.md skeleton

  • Purpose and ownership
  • Normal operating procedure
  • Verification checklist
  • Troubleshooting symptoms
  • Rollback or recovery steps
  • Escalation and maintenance notes

Reusable prompt

Use this when an AI assistant keeps blending requirements, implementation, and operations into one swampy mega-document.

Create three separate project documents for the following work: SPEC.md, PLAN.md, and RUNBOOK.md.

Keep their responsibilities distinct:
- SPEC.md defines the target behavior, constraints, non-goals, edge cases, and acceptance criteria.
- PLAN.md defines the implementation phases, files to inspect, validation steps, rollback thinking, risks, and stop points.
- RUNBOOK.md defines how to operate, verify, troubleshoot, recover, and maintain the result after it exists.

Do not put implementation guesses in the SPEC unless they are hard requirements.  Do not put routine operating instructions in the PLAN unless they are needed for implementation validation.  Mark assumptions clearly.  Include open questions where information is missing.

Field guide takeaway: SPEC.md, PLAN.md, and RUNBOOK.md are not three costumes for the same document goblin. The SPEC defines the destination, the PLAN lays the road, and the RUNBOOK keeps the lights on after arrival. When AI work is split across those lanes, review becomes sharper, assumptions become visible, and future maintainers inherit a map instead of a riddle.
