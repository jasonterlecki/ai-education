Checkpointed Execution Prompt

Use this prompt when an AI assistant or coding agent needs to complete one bounded phase, prove what it did, report clearly, and stop before it gallops into the next phase wearing a tiny hard hat.

One phase only Validate before handoff Stop means stop

The checkpoint loop

Checkpointed execution turns a large plan into reviewable slices. Each slice has a target, boundary, validation evidence, and a forced stop point so the next step starts from verified ground.

Read the phase

Point the assistant at the exact phase, requirement, ticket, or PLAN.md section. Do not ask it to hold the entire delivery saga in its little context backpack.

Inspect first

Require it to inspect current files, conventions, dependencies, and validation commands before editing. No architecture improv troupe.

Implement only the slice

Make the smallest complete change for the current phase. Later phases stay outside the fence, even if they wave snacks.

Validate the result

Run the checks that fit the change: tests, linting, build commands, screenshots, smoke tests, policy checks, or manual review steps.

Report and stop

Summarize changed files, commands run, results, assumptions, risks, blockers, and next review needs. Then stop cold until a human releases the next phase.

The practical rule

Use this prompt when AI work can affect code, configuration, documentation that drives delivery, customer-facing behavior, data, security, infrastructure, automation, or any workflow where a large unreviewed change would be painful to unwind.

Do not ask for “the whole thing.” Ask for “this phase, with proof, then stop.”

Copy-ready prompt

Replace bracketed text with the phase, plan, repo, files, and validation commands. Keep the stop rule intact. It is the little red gate with teeth.

Execution scaffold 
Role:
Act as a careful execution assistant working under checkpointed delivery.  Your job is to complete one bounded phase, validate it, report exactly what changed, and stop.  Do not continue to later phases unless explicitly instructed after review.

Assignment:
Execute [Phase number / ticket / task name] only.

Source of truth:
- Primary plan or specification: [PLAN.md, ticket, specification, runbook, design note, or pasted requirements]
- Current phase to execute: [paste the exact phase text here]
- Previous checkpoint summary, if any: [paste previous summary or write "none"]
- Repository, project, or workspace: [repo name, directory, environment, or system]

Goal for this phase:
[Describe the observable outcome that should be true when this phase is done.]

Scope boundaries:
In scope:
- [Files, directories, modules, pages, workflows, tests, docs, configs, or commands that may be touched]

Out of scope:
- [Later phases]
- [Unrelated refactors]
- [Style rewrites]
- [Feature additions not required by this phase]
- [Anything else that should not be changed]

Protected areas:
Do not touch these unless the current phase explicitly requires it and you explain why before editing:
- [Protected files, directories, credentials, auth pages, production configs, database migrations, infrastructure, generated files, vendor files, or sensitive workflows]

Constraints:
- Implement this phase only.
- Preserve existing behavior unless this phase explicitly changes it.
- Do not invent requirements, approvals, owners, data access, architecture, or security acceptance.
- Do not perform unrelated cleanup, formatting, renaming, dependency changes, or refactors.
- Do not modify secrets, credentials, tokens, keys, production settings, or access controls unless the phase explicitly requires a reviewed placeholder or documented configuration change.
- If a required detail is missing, stop and ask or document a safe assumption before continuing.
- If the requested work conflicts with existing instructions, policy, tests, security rules, or protected areas, stop and report the conflict.

Inspection step:
Before editing, inspect the relevant existing files, conventions, commands, and tests.  Briefly identify:
- Files or areas inspected
- Existing patterns that must be followed
- Validation commands available
- Any ambiguity, contradiction, or missing context

Execution step:
Make the smallest complete change that satisfies this phase.  Keep the diff focused.  If you discover additional work that belongs to a later phase, record it as a follow-up instead of implementing it now.

Validation step:
Run the validation that matches the touched work, such as:
- [unit test command]
- [integration test command]
- [lint command]
- [type check command]
- [build command]
- [format check command]
- [security or policy check]
- [manual smoke test]
- [screenshot or UI check]

If a validation command cannot be run, state why, what evidence is missing, and what a human should run next.

Stop conditions:
Stop immediately and report if:
- The phase requires access, approval, credentials, or environment permissions you do not have.
- The phase would require touching protected areas not named in scope.
- The implementation would change behavior outside this phase.
- Existing tests or files contradict the plan.
- Required requirements are missing or ambiguous.
- Validation fails and the cause is not safely fixable inside this phase.
- The work reveals a security, privacy, data, production, or rollback risk not covered by the plan.

Required final report:
Return a checkpoint report with these sections:

1. Phase executed
   - Phase name or number
   - Goal
   - Completion status: complete, partial, blocked, or not started

2. Files changed
   - File path
   - Summary of change
   - Why the change belongs to this phase

3. Files inspected but not changed
   - File path
   - Why it was inspected

4. Validation performed
   - Command or check
   - Result
   - Evidence or notable output

5. Validation not performed
   - Command or check not run
   - Reason
   - Who should run it or what is needed

6. Assumptions made
   - Assumption
   - Why it was safe enough for this phase, or why it needs review

7. Risks and blockers
   - Risk or blocker
   - Impact
   - Recommended mitigation or decision needed

8. Follow-ups for later phases
   - Follow-up item
   - Why it was not implemented now
   - Suggested phase or owner, if known

9. Review checklist for the human
   - What should be reviewed before accepting this checkpoint
   - What evidence should be checked
   - What should be confirmed before starting the next phase

10. Stop confirmation
   - State clearly: "I have stopped after this phase and will not proceed to the next phase without explicit instruction."

Task:
Execute [Phase number / ticket / task name] only using the rules above.

What to feed the checkpoint

A checkpoint prompt works best when the assistant receives the current phase, the boundary fence, the validation commands, and the stop conditions. Otherwise, the agent may turn helpfulness into sprawl.

The exact phase Paste the current phase from the plan or ticket. Include the objective, expected output, and anything explicitly excluded.
The protected areas Name the files, pages, folders, secrets, infrastructure, migrations, and workflows that should not be touched without review.
The validation commands Give the agent the tests, build commands, lint checks, smoke tests, screenshots, or manual review steps that prove the phase did not wobble.
The current context Include prior checkpoint summaries, known blockers, conventions, relevant architecture notes, and decisions already made.
The stop line Tell the agent exactly when to stop: after the phase, on missing permissions, on validation failure, on contradiction, or on scope expansion.
The report format Require changed files, validation results, assumptions, risks, blockers, and human review items. A vague summary is review confetti.

Weak prompt

This sounds efficient, but it gives the agent too much room to wander, overbuild, or silently reinterpret the plan.

Implement the plan and fix anything you find.
  • No phase boundary.
  • No protected files or systems.
  • No validation requirement.
  • No stop point.
  • No report format.
  • No distinction between required work and nice-to-have cleanup.

Stronger prompt

This version defines the slice, the fence, the proof, and the human review gate. It is slower than chaos and faster than archaeology.

Implement PLAN.md Phase 2 only: add draft preview support to the admin page editor.

Before editing, inspect the current editor files, preview-related routes, and existing validation commands.

In scope:
- Admin page editor preview behavior
- Preview route or handler if Phase 2 requires it
- Tests or smoke checks related to preview

Out of scope:
- Publishing workflow
- Import/export
- Role or permission model changes
- Legacy SQL-backed pages
- Authentication pages
- Public form receiver work

Protected areas:
- Production configuration
- Secrets and credentials
- Database migrations unless Phase 2 explicitly requires one
- felix_users.php
- felix_admin.php

Validation:
- Run available syntax checks for changed PHP files
- Run available frontend/build checks if assets are changed
- Describe one manual preview smoke test
- If a check cannot be run, state why

When finished, stop and report:
1. Files changed
2. Files inspected but not changed
3. Validation run and results
4. Assumptions
5. Risks or blockers
6. Follow-ups for later phases
7. Human review checklist
8. Confirmation that you stopped after Phase 2

Stop conditions worth repeating

These are the little tripwires that keep a checkpoint from becoming an unsupervised expedition. Put them in the prompt when the work is more than a throwaway draft.

Missing authority The work needs credentials, approvals, production access, or permission changes that were not already granted.
Scope expansion The agent finds related work, cleanup, refactors, or future-phase items that are useful but not part of this checkpoint.
Contradiction The plan conflicts with existing code, repo instructions, tests, policy, security rules, or stakeholder requirements.
Failed validation A check fails and the fix is not clearly inside the current phase. Do not let the agent tunnel into unknown plumbing.
Protected area The work would touch auth, secrets, IAM, DNS, database migrations, production config, customer data, or other fenced systems.
Unclear requirement The agent cannot tell which behavior is intended, who owns approval, or what “done” means in observable terms.
New risk discovered The phase reveals security, privacy, reliability, accessibility, data, cost, or rollback risk that the plan did not cover.
Next phase temptation The current slice is done, but the next slice looks obvious. That is exactly when the agent should report and stop.

What a good checkpoint report gives the next run

The report should become a clean baton pass. A later assistant, reviewer, or engineer should understand what happened without spelunking through the whole chat transcript.

Diff map Changed files, why they changed, and how each change maps to the phase. No mystery meat commits.
Proof of validation Commands, checks, results, and anything not run. “Looks fine” is not a validation strategy.
Assumption ledger Every assumption that influenced the work, especially the ones a human should confirm before the next checkpoint.
Risk trail Risks found, blockers hit, mitigations used, and decisions needed. This keeps uncertainty visible instead of varnished.
Follow-up parking lot Useful work discovered but not implemented because it belongs to a later phase, backlog item, or separate approval path.
Explicit stop A clear statement that the agent stopped after the current phase and did not continue without review.

Fast decision matrix

Use checkpointed execution whenever the cost of a wrong assumption is higher than the cost of another review turn.

Situation Use checkpointed execution? Why
Drafting a throwaway outline or brainstorming names. Usually no. The blast radius is tiny and the output is easy to discard.
Editing production-adjacent code or configuration. Yes. Small slices make review, validation, and rollback easier.
Implementing a PLAN.md with multiple phases. Yes. Each phase should become its own execution unit with a report and stop point.
Changing authentication, authorization, secrets, data access, or infrastructure. Yes, with stricter gates. Permissions and security boundaries should never be changed by broad “just finish it” prompts.
Large refactor across many files. Yes. Focused checkpoints reduce accidental behavior changes and make reviewers less likely to miss the raccoon in the ductwork.
Simple documentation typo or isolated copy edit. Optional. A tiny change may not need a full checkpoint, but a short report is still useful if the document drives operations.
Prompt library takeaway: Checkpointed execution is how you keep AI work reviewable. Give the assistant one bounded phase, make it inspect before editing, demand validation evidence, collect a report, and stop before helpfulness turns into a tiny bulldozer with opinions.
