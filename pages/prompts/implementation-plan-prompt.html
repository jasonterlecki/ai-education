Implementation Plan Prompt

A reusable prompt for turning a chosen direction into scope, non-goals, phases, validation, rollout, rollback, risks, and acceptance criteria. Use it when the idea has left the brainstorming meadow and is approaching real systems, real people, real data, or real consequences.

What the plan must force into the open

An implementation plan is not a prettier brainstorm. It is the moment the team starts naming boundaries, dependencies, controls, stop points, and proof that the work is actually ready.

1

Chosen direction

State the selected approach, the decision already made, and what problem this plan is meant to solve. Do not reopen the entire idea maze unless there is a blocker.

2

Scope

Define what is included, which users or workflows are affected, what files or systems may change, and where the delivery boundary begins and ends.

3

Non-goals

Fence off tempting extras, unrelated refactors, future ideas, protected pages, experimental shortcuts, and anything that should not sneak into the work.

4

Phases

Break delivery into reviewable slices with clean stop points. Each phase should have a purpose, affected components, validation, and a handoff summary.

5

Validation

Name the checks before the work starts: tests, linting, screenshots, smoke tests, security review, accessibility review, data checks, and human review.

6

Rollout

Explain how the change reaches users: dev first, feature flag, pilot group, staged release, communications, monitoring, support notes, and approval gates.

7

Rollback

Describe how to retreat without drama: restore path, disable switch, data reversal limits, configuration rollback, owner, and conditions that trigger the rollback.

8

Acceptance criteria

Define what “done” means in observable terms. A plan without acceptance criteria is just a confident map drawn on a napkin during turbulence.

The practical rule

Use this prompt after a direction has been selected and before controlled delivery begins. The output should be concrete enough for humans, engineers, AI coding agents, reviewers, and approvers to understand what will change, what will not change, how the work is validated, and where to stop.

Exploration chooses the path. An implementation plan builds the guardrails before anyone drives.

Copy-ready prompt

Replace bracketed text with your situation. Keep the review, rollback, and non-goal sections when the plan may guide actual delivery or an AI coding agent.

Plan scaffold 
Role:
Act as a careful implementation planning assistant.  Your job is to turn a chosen direction into a controlled delivery plan.  Do not write code.  Do not assume approvals, hidden requirements, or unstated architecture.

Goal:
Create an implementation plan for [chosen direction, feature, workflow, migration, policy, page, automation, integration, or operational change] so [audience or team] can deliver it safely, review it, validate it, roll it out, and roll it back if needed.

Chosen direction:
[Summarize the direction that has already been selected.  Include the reason it was chosen and any alternatives that were rejected, if relevant.]

Context:
Current state: [what exists today]
Desired outcome: [what should be true after delivery]
Users or workflows affected: [who or what changes]
Systems, repositories, pages, services, data, or processes involved: [known components]
Known constraints: [policy, security, privacy, architecture, budget, timing, tooling, accessibility, compliance, brand, support, etc.]
Known dependencies: [people, systems, approvals, data, vendors, environments, APIs, credentials, documentation, etc.]
Known protected areas: [files, pages, systems, data, permissions, workflows, or behaviors that must not be changed]
Known non-goals: [what this plan must not include]
Source material: [paste the approved direction, vibe brief, requirements, notes, examples, screenshots described in text, or stakeholder comments]

Constraints for the plan:
- Separate facts, assumptions, open questions, and recommendations.
- Do not invent approvals, deadlines, budgets, owners, architecture, data access, or security acceptance.
- Include explicit scope and explicit non-goals.
- Preserve existing behavior unless a change is explicitly required.
- Identify risks, dependencies, review gates, and escalation points.
- Include a phased delivery path with checkpointed stop points.
- Include validation for each phase, not only final validation.
- Include rollout, rollback, monitoring, support, and communication considerations.
- Flag anything that requires security review, privacy review, legal review, architecture review, procurement, leadership approval, change management, or incident-response planning.
- If information is missing, list it clearly and explain whether the plan can proceed with assumptions or must pause.

Output format:
Return the implementation plan with these sections:
1. Executive snapshot
   - Goal
   - Chosen direction
   - Intended outcome
   - Delivery confidence
   - Key risks
   - Recommended next approval or review

2. Scope
   - In scope
   - Out of scope / non-goals
   - Affected users, workflows, systems, repositories, pages, data, or teams
   - Protected areas that must not be touched

3. Current-state assumptions
   - Known facts
   - Assumptions
   - Missing information
   - Contradictions or unclear requirements

4. Proposed delivery model
   - Recommended implementation approach
   - Major components or workstreams
   - Ownership suggestions, if owners are not already assigned
   - Dependencies and sequencing

5. Phased plan
   For each phase include:
   - Purpose
   - Work included
   - Work explicitly excluded
   - Files, systems, workflows, or stakeholders likely involved
   - Validation required
   - Review gate or stop point
   - Risks and mitigations
   - Handoff notes for the next phase

6. Validation plan
   - Automated checks
   - Manual review
   - Security, privacy, accessibility, or compliance checks
   - Test data or environment requirements
   - Evidence that should be captured

7. Rollout plan
   - Environment sequence, such as dev, test, pilot, production
   - Feature flags or controlled release options
   - Communication needs
   - Monitoring and success signals
   - Support or training needs

8. Rollback plan
   - Rollback trigger conditions
   - Technical rollback steps
   - Data rollback limits or irreversibility warnings
   - Communication during rollback
   - Owner or decision point for rollback

9. Risk register
   For each risk include:
   - Risk
   - Impact
   - Likelihood
   - Detection method
   - Mitigation
   - Escalation path

10. Acceptance criteria
   - Functional criteria
   - Safety and control criteria
   - Review and approval criteria
   - Documentation criteria
   - Operational readiness criteria

11. Open questions and decisions needed
   - Questions blocking delivery
   - Questions that can proceed with assumptions
   - Decisions needed before Phase 1
   - Decisions needed before production rollout

12. Recommended next action
   - What should happen next
   - Who should review the plan
   - Whether this is ready for a PLAN.md, specification, runbook, ticket breakdown, or AI coding-agent execution prompt

Review criteria:
Before finalizing, check whether the plan:
- Has clear scope and non-goals
- Does not smuggle in invented facts or approvals
- Breaks work into reviewable phases
- Defines validation before implementation begins
- Names rollout and rollback paths
- Makes risks, assumptions, and missing information visible
- Protects sensitive systems, data, permissions, and existing behavior
- Gives reviewers enough detail to approve, reject, or revise the plan

Create the implementation plan from the material below.

How to feed the plan engine

The prompt works best when the direction has already been chosen. Feed it the decision, the constraints, the existing reality, and the places where the work must not wander.

Start from a chosen direction Use a vibe brief, decision note, stakeholder agreement, or selected option. The planning prompt should not reopen every possible path unless the chosen path is unsafe.
Name the real boundary List systems, files, pages, users, roles, environments, data, workflows, and support teams affected by the change.
Protect non-goals State what must not be changed. This is especially important when AI agents may later modify files, configs, prompts, policies, or infrastructure.
Demand phases Ask for bounded slices with stop points. Big-bang implementation is how small assumptions become architectural raccoons in the ceiling.
Require proof Validation should be named before work begins. Include test commands, review checks, screenshots, data checks, logs, and evidence to capture.
Plan the retreat Rollback is not a pessimistic garnish. It is a design requirement whenever the change can affect users, data, money, security, or public behavior.

Weak prompt

This asks for a plan, but it does not give enough boundary, risk, or validation structure. The AI may produce a confident checklist that quietly ignores delivery reality.

Make an implementation plan for this feature.
  • No chosen direction or current state.
  • No scope, non-goals, or protected areas.
  • No requirement for phased execution.
  • No validation, rollout, rollback, or acceptance criteria.
  • No instruction to separate facts from assumptions.

Stronger prompt

This version turns a selected direction into a delivery artifact that reviewers can inspect before an engineer or AI coding agent starts changing things.

Act as a careful implementation planning assistant.  Do not write code.

Chosen direction: Add editable education pages to the existing site through a super-admin controlled page editor.

Context:
- Existing static and dynamic pages must continue working.
- Legacy SQL-backed pages, such as Meet the Foxes and Stories, should not be migrated in this phase.
- The admin console should support preview, save draft, publish, import, and export.
- Implementation begins in DEV and only moves to PROD after review.
- Do not modify authentication pages or unrelated public forms.

Create a plan with:
1. Executive snapshot
2. Scope and non-goals
3. Current-state assumptions and missing information
4. Phased delivery plan with stop points
5. Validation plan for each phase
6. Rollout plan
7. Rollback plan
8. Risk register
9. Acceptance criteria
10. Open questions
11. Recommended next action

Separate facts from assumptions.  Flag anything requiring security, privacy, architecture, or production approval.

Review before the plan becomes marching orders

A polished implementation plan can still be wrong. Review it for hidden assumptions, unsafe scope, missing rollback, vague validation, and places where the AI filled silence with confident wallpaper.

Scope discipline Check whether the plan respects non-goals, protected areas, existing behavior, and the actual chosen direction.
Phase quality Each phase should be independently reviewable, validated, and stopped before later phases depend on it.
Operational reality Look for deployment steps, monitoring, support, communications, ownership, rollback, and evidence capture.
Approval boundary Confirm who must review the plan before delivery, especially for security, privacy, infrastructure, money, or public workflows.

Customization matrix

Situation Add this to the prompt Review especially for
Website feature or content system. Existing pages, routing, templates, preview behavior, admin roles, publishing workflow, import/export needs, and pages that must not be touched. Broken legacy behavior, missing mobile review, weak preview rules, accidental migration of excluded pages, and unclear publish rollback.
Data migration or coexistence model. Source and target data, compatibility window, read/write ownership, migration order, backout limits, reconciliation checks, and audit evidence. Irreversible steps, partial migration states, missing reconciliation, unclear freeze windows, and hidden reporting impacts.
AI coding-agent execution. Repository map, allowed files, protected files, branch strategy, validation commands, stop points, reporting format, and review requirements. Scope creep, unrelated refactors, untested edits, stale context, missing command output, and changes that bypass human review.
Infrastructure or IaC change. Terraform workspaces, Kubernetes contexts, IAM scope, DNS, certificates, networking, plan review, state handling, and emergency rollback contacts. Privilege expansion, production context mistakes, DNS or certificate outages, state drift, and automation that can repeat damage quickly.
Security or privacy-sensitive workflow. Data classification, secrets handling, vendor boundaries, DLP, logging, incident triggers, escalation paths, audit trail, and approved tools. Leaked data assumptions, prompt injection paths, weak access controls, missing auditability, and unclear incident ownership.
Training, adoption, or communication rollout. Audience segments, role-based guidance, champions, training assets, feedback loops, metrics, support channels, and expectations to correct. Overpromising, vague ownership, poor feedback capture, missing success metrics, and communication that implies approval before approval exists.
Prompt-library takeaway: An implementation plan turns a chosen direction into controlled delivery. Use it to name scope, non-goals, phases, validation, rollout, rollback, risks, and acceptance criteria before work begins. The better the plan, the less the project depends on hope wearing a hard hat.
